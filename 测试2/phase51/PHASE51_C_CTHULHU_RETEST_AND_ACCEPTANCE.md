# C｜克苏鲁追船重复生产与分项验收

前置：阅读 [总控](PHASE51_00_EXECUTION_GUIDE.md)，A 的关键正确性与效率修复可用，B 的质量修复已集成。只复测本题，不等待豆包，不引入 Grok 执行链。

## C1. 固定作品负荷，避免把简单任务当提速

使用现有写实“克苏鲁追船”项目的故事事实：船长与大副两人、同一艘船、同一怪物和追击空间。保留原剧情的重要危险、关键动作、选择与结果；根据已批准事实核对，不凭历史讨论猜具体结局。

有现成完整分镜和资产时，先冻结该输入用于比较，不重新生成全部角色与船。如果原计划存在 B 已证明的问题，保存原计划并说明必要调整，再冻结修正版。两种计划负荷不同就明确标记，不能直接给出纯系统速度的因果结论。

缺少完整计划时，让现有编剧与导演按正式 Skill 形成一条完整故事：追击建立、压力升级、人物采取行动、行动产生结果，避免只有怪物露面和船在跑。无现成时长约定可先规划约一分钟，镜头数由剧情决定；通常可从约 8–12 镜起步，但这不是硬指标。源视频每镜至少 8 秒、默认 10 秒；剪后时长按动作与节奏选择。

对照使用原项目实际时长和关键事件覆盖。改变时长、镜头数、源生成总秒数、动作负荷或参考资产时，列出差异。相同故事负荷下的提速与改善剪辑／规划产生的收益分别报告。

无旁白、无主动 TTS；保留合格原生音效。重点检查写实感、双人身份、船与怪物、追赶关系、关键动作和接缝，不以角色隐藏在暗处或把怪物全删掉来获得虚假的一致性。

## C2. 冻结后运行，不混用改动前后的结果

记录代码提交与 dirty diff 指纹、工作流版本、Skill 版本、模型与模式、Thinking、并发与限流配置、故事及镜头计划、资产版本、检查规则、缓存政策和输出规格。所有运行都保留这份快照。

分两类证据：

1. **固定计划复验**：相同故事、镜头计划及必要资产，六个系统 Agent 使用正式入口执行。用于验证修复后的运行可靠性和可测效率。
2. **自主方法检查**：在全新系统 Agent 会话中，仅提供作品目标、已批准事实和正式 Skill，不给它逐镜路径答案。确认它会自行选择接续、重建或正常切镜。可放在固定计划复验的一次运行中：固定叙事任务，方法由 Agent 决定；方法差异应记录，不能视作严格运行层 A/B。

Claude Code 负责记录、故障测试和核验，不直接代写逐镜 prompt、补交正常生产的视频或替用户正式选片。不得通过执行侧脚本绕过导演然后宣称六员自主成功；若为诊断必须这样做，另开标为诊断的尝试。

允许复用固定资产，视频候选必须区分新生成与复用。不同轮完整视频都来自缓存时，只能证明恢复／复用效率，不能称三次独立视频生产成功。

## C3. 测试顺序与次数

| 步骤 | 任务 | 新生成的范围 | 要回答的问题 |
|---|---|---|---|
| C-T01 | 重放 A 的关键失败与恢复 | 优先无生成的故障注入／事件重放 | 有效成果、job 和候选能否保留并推进 |
| C-T02 | 同计划短序列前后比较 | 同一小序列，已有可靠 A 证据可直接复用 | 系统改动本身缩短了哪些区间 |
| C-T03 | 冻结版完整生产第 1 次 | 必要的完整镜头视频；素材可复用 | 能否交出首个完整、可审片候选 |
| C-T04 | 冻结版完整生产第 2 次 | 独立生成候选，复用同等资产准备 | 改善能否重复，首次失败是否仍可恢复 |
| C-T05 | 冻结版完整生产第 3 次 | 新会话、独立生成候选 | 方法会不会自主选择，流程与质量是否稳定 |
| C-T06 | 已批准版本的正式装配与用户交接 | 只重导出必要版本 | 最终片是否使用正确选片和真实裁切 |

三个完整运行均记录首次尝试和全部返工；每次可在既有允许范围内局部修复候选，不改变冻结代码与 Skill。出现代码／Skill 缺陷时，保存该轮失败，修复后建立新快照并重新完成受影响验证；不同快照不拼成“三轮都通过”。无关回归不重复整套。

三轮是有限样本，不能给出总体稳定成功率承诺。若三轮中出现影响结论的失败，解决能够定位的原因再按需要复验，不无上限刷结果。运行异常进入明确阻塞状态，保存恢复依据；不能让任务无提示空转二十小时。

已有旧基线能覆盖相同工作负荷时，直接引用原始证据。没有可靠基线，先做 C-T02 的受控比较；历史长耗时只用作背景，不为凑“三轮旧版”重新跑坏系统。受控系统区间证据与新版本重复生产仍然可交付，但完整任务提升百分比应标为暂缺可靠对照。

## C4. 效率表必须包含失败和返工

每轮至少列：开始、首个可播放候选、首个满足自动质量门槛候选、最后交付时刻；人工阻塞区间；系统耗时；可消除损耗；上游实际受理至本地发现；文本回合与排队；查询量与 429；生成次数；累计生成秒数；重复提交；重复写入／渲染；返工镜头数；人工技术介入次数。

原始请求、生成、查询、下载、审查和导出耗时分开列，重叠另注明。不能把首次失败从总时间抹掉，也不能只统计修复后最后成功那一次。

相同口径下：

`完整任务提速比例 = 1 - 修复后 T_system 中位数 / 可比较基线 T_system 中位数`

小样本同时列三轮原值与范围；仅三条数据不用 p95 包装稳定性。基线只有一条就明确这是单基线观察值；不同服务窗口、缓存、模式、任务量或质量标准可能影响结果时说明差异，不作单因归因。

另报 `T_avoidable` 的绝对分钟数及下降比例，列出每项被消除的系统损耗。上游完成时间未知时，不把“受理至发现完成”命名为纯模型生成时间。

可附“每分钟成片的系统耗时”“每秒可用片段所需生成秒数”和“可剪有效秒数／源素材秒数”作辅助；这些不能代替同负荷对照，不能鼓励删关键动作或拉长静止画面。

## C5. 画面与连续性门槛

| 项目 | 自动审查候选的要求 | 用户判断的内容 |
|---|---|---|
| 人物 | 保留片段无身份交换、分身、意外第三人或明显身体变形 | 两人是否像同一人，表情与动作是否自然 |
| 船与怪物 | 关键结构和外观稳定；尺度与方位变化有依据 | 写实质感、威胁感是否可接受 |
| 动作与剧情 | 危险、行动和结果可读；关键过程未被剪掉 | 追击是否成立，故事是否有张力 |
| 接缝 | 全部相邻边界有检查，正常切镜与连续动作分别判定 | 是否突兀，有没有妨碍观看的跳跃 |
| 裁切与依赖 | 实际保留区间、接力端点和下游引用一致 | 剪辑节奏是否顺畅 |
| 技术流 | 无缺镜、误用旧版、黑帧、重复片段、意外冻结或输出规格错误 | 完整播放体验 |
| 音效 | 合格原生音效保留；无明显错位、失真或突断 | 声音是否连贯、合适 |

自动门槛：保留区间内关键失败为零、明显失败为零。轻微问题在保留区间中仍存在时，要标为“有已知瑕疵的候选”，不能写“无瑕疵通过”。必要时局部修复，再重新审查对应镜头和接缝。

逐镜评分可使用 0=失败、1=有可见问题、2=可接受，但硬失败优先，不能靠平均分掩盖一个人物分身镜头。保留全片播放、关键动作和接缝片段；抽帧审查覆盖不足时如实标记，交给用户看完整视频。

本轮只判现有系统作品是否可用。与 Grok 的完整效果对比尚未控制模型、规划和人选因素，不把“用户觉得差距缩小”改写成实验已证明等效。

## C6. 收尾判定与用户反馈

| 结论 | 应采用的表述 |
|---|---|
| 修复有证据、系统区间变快，完整任务达到 A 的 30% 目标，画质门槛满足 | 效率目标达到；自动质量验收通过，用户评价另列 |
| 确有系统提速，但总体目标未达到或旧基线不足 | 效率改善已验证；总体目标未达／暂无法量化，说明剩余瓶颈 |
| 比以前快，但人物、动作或接缝仍失败 | 效率改善；成片质量未通过，列明失败镜头 |
| 画面改善，但仍整轮重启或长时间空转 | 质量改善；系统效率未通过 |
| 两者自动门槛满足，但用户尚未看片 | 可交用户评审；不得记为用户验收完成 |

至少交出一个完整可播放候选，不只交两三个好镜头。原片、首次粗剪和最终修复版分别保留；可以选最好候选，但不能抹掉其他轮失败。正式 final_render 仍由现有用户入口和授权决定。

用户评审材料一次整理：完整候选、重点修改前后片段、全片时间点问题表、实际耗时表、待决定事项。先展示具体结果，用户看片不作为 Claude Code 提前停止独立修复与整理的理由。
