# A｜生产系统效率与失败恢复

前置：阅读 [总控](PHASE51_00_EXECUTION_GUIDE.md)。本批负责实证定位和修复系统损耗；不扩大并发。字段与状态名称均为语义示例，复用现有实现。

## A1. 先取得能定位问题的最小基线

读取 AGENTS.md、当前注册表、工作流运行入口、正式 Skill、配置、任务委派与恢复、视频提交及收货、人工审核、选片和装配路径。记录提交号、未提交 diff 标识、配置指纹、模型和 Skill 版本。保留现有用户改动。

优先取最近克苏鲁项目的一次完整运行、一次重试／恢复和一次长停顿；旧二十小时运行有完整证据时再补入。沿 run→node→task→provider job→artifact→review→selection→render 建立关联。报告只是找证据的入口。

不要重跑一遍二十小时来证明它慢。先利用旧日志和现有产物重建；缺事件时补最少的计时点，然后运行一个能复现瓶颈的小任务。若某个外部服务长期不可用，先停止无意义重发，保留原因，推进可独立完成的代码与恢复验证。

### 需要对齐的时刻

| 时刻 | 含义与记录要求 |
|---|---|
| 计划确定 | Agent 已给出合法方案；区分尚需创作决策与纯执行 |
| 输入就绪 | 依赖、资源、版本、权限、必要审核和提交计划均满足 |
| 提交开始／受理／ID 落盘 | 三个时刻分别记录，不能只保留最后回复 |
| 上游完成／本地发现 | 上游完成时间只有真实可得才记录；未知填空，不倒推 |
| 下载／候选入库／审查完成 | 区分生成、收货、审核与写回 |
| 正式选片／装配／导出 | 区分候选预览与正式版本 |
| 暂停／恢复／局部返工 | 原因、对象、旧任务及产物是否复用 |

额外记录：文本调用排队和响应时间、回合数、输入体量、工具耗时、重读次数、轮询次数、本地拒绝及上游错误来源。仅保留脱敏请求摘要和必要证据，不记录秘密或模型内部思维链。

### 时间口径

- `T_preview`：用户启动到首个完整可播放候选交付的墙钟时间，包含失败与恢复。
- `T_reviewable`：启动到首个达到本轮自动质量门槛的完整候选。与 T_preview 分开；没有达到就标为未达成。
- `T_human_blocked`：在完成路径上确实因必要人审而停止、且无获准工作可继续的区间并集。不能把审核打开期间仍在生成的时间全扣掉。
- `T_system`：对应目标的墙钟时间扣除上述必要人工阻塞。仍包含 Agent 推理、系统等待、上游排队生成、审查、返工、收货和导出。
- `T_avoidable`：有逐段证据证明可以取消或缩短的等待、重复劳动和错误恢复损耗。不能等同于“没有视频在途”。

任务累计耗时和用户墙钟时间分别列；有重叠就用区间并集。总体分账应在一条主时间轴上按实际阻塞原因归类，子任务统计作为附表，不能相加后当总体。多任务和文本调用重叠时，列出重叠或用因果路径解释，不强求虚假的可加数字。每段长空档标明：依赖、创作决策、审查、人工、本地限流、上游处理中、I/O、异常恢复、就绪未推进或未知。未知不得写成已查明的系统浪费。

## A2. 按证据处理以下高价值缺陷

### ① 承认有效成果，补缺项而非重做整轮

检查现有“本回合新增写入”与节点完成条件是否耦合。恢复时能以真实当前状态证明任务满足，应支持既有成果交接；纯核验或纯复用无需制造一次无意义写入。

复用至少同时验证：对象与任务一致；生成依据及输入版本匹配；真实回执和资产可读取；必要审查状态满足；没有取消、过期、替换或 stale；复用和后续写入符合 ownership／OCC。数量相同、文件存在、Agent 声称完成均不足够。

按缺项恢复：已受理任务继续查询；已完成任务补下载；有候选未审查就补审查；有合格素材未交接就补交接。视频生成成功不代表视觉合格，视觉通过也不自动成为用户正式选片。

### ② 持久化提交与恢复，防止不明提交被重复生成

先保存请求依据和提交意图，受理后尽早保存 job ID；定义提交中断、受理后中断、下载中断、回复失败各自的恢复路径。身份标识应覆盖运行、节点、尝试和不可变输入依据，不只使用镜头名称。

| 情形 | 正确推进 |
|---|---|
| 明确未发出／未受理 | 按错误类别重试或修输入 |
| 已有 job ID | 查询、收货原 job，不重新提交 |
| 请求可能受理但 ID 丢失 | 标为提交结果不明，先用上游幂等／查询能力对账 |
| 上游不支持对账且结果不明 | 隔离该尝试并诚实报告，不能无证据宣称“安全重发” |
| 回执已到但 Agent 最后回复失败 | 修回复或交接，不抹掉真实成果 |
| 晚到旧结果 | 留在原尝试，不覆盖新版本和正式选片 |

在没有上游幂等保障时，不承诺 exactly-once。重复回调、重复 resume 和重复点击应在本地尽量做到状态写回及后续动作幂等，不能把同一个 job 登记为两个候选。

### ③ 让已经确定的工作及时推进

确认长空档是否来自导演回合、重读上下文、同步工具阻塞、资源锁、固定 sleep、遗漏唤醒或完成事件未投影。只有定位后才修改。

导演负责创作选择、方法选择、失败诊断和审查判断；运行层执行已经批准且输入就绪的计划，包括提交、查询、下载和交接。不得让每次查询或每条 receipt 都触发完整导演推理、重复规划和重新征求提交许可。

若计划未确定、输入不合法、gate 尚未通过或新素材改变了创作判断，仍由对应 Agent 决定。尾帧依赖要等待实际可用端点。系统不能替导演拍摄未决定的镜头，也不能越过人工 gate。

优先用现有事件、持久化任务和恢复机制补足“完成→下一步”的推进。事件重复或漏发时可用轻量对账补偿，避免建设新的通用调度平台。重启后恢复原任务和已获准计划；无效旧计划标为需要重新判断。

为长任务留下当前阻塞原因、最后进展、下一次唤醒和处理期限。轻量停顿检查发现就绪任务长期未推进时应恢复调度或明确报错，不能只追加“继续等待”的模型回合。HTTP 请求超时与上游 job 处理期限分开：合理的上游等待依据真实完成分布与服务限制配置，不因两分钟没有进展就杀掉正常 job；超过期限仍保留受理记录并查询／对账，不能自动当作未提交重新生成。

### ④ 查询与文本调用共用额度时减少竞争

查清限流归属：真实账号限制、模型或 endpoint 限制、本地保守配置、全局共享桶、多个进程共用 key。429 必须区分上游返回与本地生成。历史文档额度不能直接用于调高生产配置。

实现或修正：同一个 job 只有一个有效查询者；状态缓存供 Agent／UI 使用；轮询按实际完成分布退避并遵守 Retry-After；抖动避免集中请求；正常文本及提交请求有公平推进机会。若上游额度共享，本地分类调度仍必须守总额，不能通过拆桶虚增权限。

没有 webhook 就不要假设它存在。频率由实际延迟和额度校准，不机械固定每五秒一次，也不能过度退避导致已完成视频长期没人收货。分别报告查询量、真实 429、检测延迟和文本排队变化。

### ⑤ 消除重复 I/O、无效上下文和装配返工

只在计时证明占比可观时处理：同一媒体反复下载上传／转码／抽帧，同一版本反复审查，全量 canonical 和历史对话反复塞入每个模型回合，已完成渲染被重复启动。

缓存必须绑定素材内容或版本、输入依据和检查条件；URL 到期需要更新可访问地址，不必重新生成图片。同一请求语义的有效素材可复用，改变角色、场景状态、裁切端点或 Skill 检查条件则重新判断。缓存命中也留下来源证据。

缩减上下文时使用当前任务、必要事实、批准资产及版本、差异和可检索索引；保留连续性、权威规则、失败证据和权限约束。不得只留“上一轮说完成”。Thinking 保持开启；确定性的查询和格式处理由代码执行即可。

装配基于明确的候选时间线快照。镜头改动只重新处理受影响片段和必须重导出的成片；不要重新生成所有源视频。用户审片前先做技术筛查，避免导出一个缺镜头或明显冻结的文件供人浪费时间。

### ⑥ 局部返工与审核语义

确认当前 reject 的正式含义。不能把旧“驳回停止”悄悄改成自动返工。最小方案是保留该含义，提供清楚的修复目标与正式 resume／repair 路径，记录用户要求、失败项和修复范围。

缺失局部修复能力且证据表明导致整轮重做时，在现有入口内补一个受约束的“修指定节点／镜头、保留合格部分”的动作；无需新增画布组件或回环。修复上游后只复核真实受影响依赖，OCC 与 stale 检查照常。取消、终止和退回修改必须可区分。

必要人审尽量一次给足具体材料、版本、推荐和待决定项，避免因材料不完整反复来回。可批量呈现的素材合并交接；不取消原来必须的审核，也不把用户尚未决定的等待写成系统空转。

## A3. 验证修复确实省时间

先对定位到的问题做小范围、有意义的验证，优先重放旧事件或故障注入，避免每改一行代码就重做整片。至少覆盖下列真实路径；已存在可靠测试则复用：

| 用例 | 要证明的结果 |
|---|---|
| A-T01 有效成果恢复，无新增写入 | 正确复用，继续缺项，不生成假写入 |
| A-T02 旧成果已 stale／输入版本改变 | 不误复用；指出真实冲突 |
| A-T03 受理后重启、回执重复或晚到 | 恢复同一 job；旧结果不覆盖新选片 |
| A-T04 提交结果不明 | 先对账；无法确认则隔离，不盲目重发 |
| A-T05 查询 429／5xx 与文本请求竞争 | 守真实限额；轮询失败不重交视频；文本能推进 |
| A-T06 剪辑或上游候选变更 | 端点和依赖 freshness 正确，合格无关素材保留 |
| A-T07 用户 gate 与局部修复 | 不绕过 gate，不全片重启；正式选片不被自动覆盖 |
| A-T08 正式入口完成与下一项就绪 | 已决定动作及时推进，状态与 receipt 一致 |

然后对同一小型镜头序列作前后验证：相同输入、Skill、模型、模式、时长、检查标准、缓存状态和并发设置；运行层版本是主要变量。生成时间随机时，分别比较提交／收货／恢复等系统区间与上游等待，不用总时间单次差值当因果证据。可重放三次确定性故障场景；真实调用是否重复由未解决的不确定性决定。

## A4. 目标与放行

以下数值是本轮工程目标，不是从旧报告推导出的速度承诺。开始真实新运行前固定口径，不能测试后改门槛：

| 指标 | 阶段目标 |
|---|---|
| 错误重做与重复提交 | 修复覆盖情景中，无因有效成果被拒绝造成的整轮重启；已知受理任务不重复提交 |
| 就绪后推进 | 正常、非限流、非 gate 情景的确定性动作，输入就绪到调度启动 p95 ≤30秒；Agent 创作决策时间单列 |
| 无理由停顿 | 无无法解释且未处理的、超过两分钟的生产停顿 |
| 可消除损耗 | 可比较任务中 T_avoidable 减少至少 60% 为目标，列出绝对分钟数 |
| 完整任务耗时 | C 批同工作负荷的 T_system 中位数下降至少 30% 为目标，画质门槛同时满足 |

就绪延迟的 p95 需报告样本量；少样本直接列全部数据。平台限额或实际损耗占比不足以达到目标时，用证据解释剩余下界，明确“目标未达到”，不制造或追认更宽门槛。

A 放行至 B 需满足：主要损耗已有证据；最关键缺陷有修复与定向验证；正式入口能跑通并恢复；没有新引入的关键正确性失败。全片 30% 目标由 C 判断，不需要为等待这个数字阻止质量修复。

## A5. 交付

提交 `PHASE51_A_REPORT.md`，附简明时间轴、按损耗分钟排序的根因表、修改与测试、提交号和 diff、原任务及资产复用情况、前后小任务证据、真实限流与并发配置、未知项及 B 的可用入口。

不要以“改了缓存／用了异步／文档齐全”宣布提速。必须展示被消除的重复工作或被缩短的等待，以及正式流程实际继续推进的证据。
