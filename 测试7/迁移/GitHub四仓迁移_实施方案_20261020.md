### 3.2 新提交类别（Conventional Commits 式，兼容目录批次）

| 前缀 | 使用场景 | 例子 |
|---|---|---|
| `feat(scope):` | GPT 新功能 | `feat(producer): ...` |
| `fix(scope):` | GPT 生产缺陷修复 | `fix(director): ...` |
| `test(scope):` | 新增/调整实际测试与 fixtures（GPT 代码职责） | `test(pipeline): ...` |
| `ci(scope):` | GitHub Actions/依赖锁/报告基础设施 | `ci(mock): add cloud regression workflow` |
| `docs(scope):` | STATE/README/架构/Pages 导航 | `docs(state): document immutable baselines` |
| `chore(scope):` | 明确保留/清理且不含功能变更的维护提交 | `chore(media): prune archived tracked evidence` |
| `archive(scope):` | C 分类档案和版本交接包 | `archive(phase52): index final reports` |
| `data(scope):` | B 冻结结构化批次 | `data(phase52): publish frozen ledgers` |
| `assets(scope):` | B 已核准静态资产样例 | `assets(phase52): add reviewed image set` |
| `manifest(scope):` | B/C 哈希和源路径索引 | `manifest(phase52): add SHA256 provenance` |
| `collab(scope):` | GPT 交接**文档/包归档**，不是替代功能 fix | `collab(handoff): archive repair round 81 status` |
| `revert:` | 回滚迁移新提交 | Git 原生 `git revert` 信息 |

**分类规则**：每次 commit 只处理同一职责和一份可审查的路径清单；不允许 `git add -A`、自动扫目录“全提交”；补丁改变核心行为时使用 `fix`/`feat`，不要用 `collab` 掩盖源码变更。每批记录 `源路径 → 目标仓/路径 → SHA256 → commit`。

## 6. GitHub Actions：动画工作流云端验证的可接受实现

### 6.1 不应把“pytest 会运行”误判为“云端动画流水线通过”

设计至少三个逻辑层，实际脚本和测试名**从 A 仓现存文件发现，不能编造**：

1. **检查与发现层**：checkout 指定 SHA → Python 3.11（若依赖要求版本不同先核实）→ 仅安装经过审核的 CI lock → `pytest --collect-only`（可行时）→ 确认 mock 标记与真实 API 禁用机制，记录 OS/Python/ffmpeg/pytest/package 锁版本。
2. **动画链路 smoke 层**：优先调用**已存在的真实测试入口**，覆盖 YAML/剧本读取 → Resource → Scene → Director → Assembly/Sequence/Producer 的 mock 流、可验证的输出 manifest/占位视频或音频路径。真实 ffmpeg 可用于零远程服务的小样本合成（如果已有测试），但 Agnes/Minimax/imgbb 等真实 API 禁止调用。不具备这种现存 smoke 时，只能报告缺口并给 GPT 开测试任务；不允许以“运行了全部 pytest”伪装已验证完整链路。
3. **全量回归层**：实际运行 `python -m pytest -q --junitxml=...` 全量 mock，上传 JUnit/XML、失败摘要、集合数、runner 环境摘要。不得误用针对特定测试筛选的少量用例冒充全量 2847 项。

### 6.2 依赖固化和环境

- 从本机 `pip freeze` 作为**参考输入**，剔除与本机绝对路径绑定/不允许公开的 local wheel/editable 包；对照 `pyproject.toml`/requirements/test plugins，形成可在 GitHub runner 重建的**CI 专用锁**（必要时 Windows 与 Linux 分开）。
- 由于生产机 Windows 11 且可能存在 Windows 路径假设，**优先以 `windows-latest`（最好固定具体已验证的 runner 镜像代号）建立可比基线**；`ubuntu-latest` 或特定 Ubuntu 镜像作为第二阶段可移植性诊断，不能把平台差异算作 A 代码回退。草案中的“Linux 先跑”可作为额外侦测，但不应取代 Windows 可比基线。
- 检查 runner 磁盘、Python 3.11、Node/Vite 是否被 Python 测试要求、ffmpeg 的真实安装状态；不能因为“常见 runner 可能预装 ffmpeg”而省略探测。
- `permissions: contents: read`；`on: push`（main/经批准的协作分支）、`pull_request`（面向 main）、`workflow_dispatch`；禁止 `pull_request_target` 检出未信任代码后运行，禁止真实生产 secrets，禁止自托管 runner、自动部署生成视频、无审批写回 main。
- 输出并保留完整 Actions run URL、触发 SHA、runner 名、run attempt 与测试工件，作为交付证据。实际的 runner 时间与平台额度依仓库设置/官方计划为准，不事先承诺测试一定绿灯。

### 6.3 291 项旧失败的正确处理（禁止“总量不增就判绿”）

基线按以下维度建档：`baseline_commit_sha`、`branch`、`runner_image`、`python_version`、`dependency_lock_hash`、`collected`、`failed_nodeids`、`error_nodeids`、`skipped`、`collection_errors`、`timeout`、`duration`。**生产与 R2、Windows 与 Linux分别记基线**。

- 首次只能得到 `UNVERIFIED_BASELINE` 或 `BASELINE_RECORDED`，不是“291 以内 = PASS”。交接报告中的约 291 是**来源说明**，需重跑并将 nodeid 清单与原始报告校准。
- 对比新运行与**同平台同依赖、已批准的冻结基线**：`new_failed_ids = current_failed_ids - baseline_failed_ids`；`new_error_ids = current_error_ids - baseline_error_ids`；并比较收集数、消失的测试、跳过集变化和超时。即使净失败数下降，只要新增其他失败，状态仍是 `REGRESSION`。
- 如果 CI 仅想展示可解释差异，可让 pytest step 在任务中保存 XML 后由最后一个对比 step 判断失败/成功；**不可使用 `continue-on-error` 将测试的未知失败直接涂成绿色**，也不能对任意 291 失败自动忽略。
- 如原先本机 291 而云端 350，先区分“环境差异/缺依赖/真实测试回退”，标 `INFRA_BLOCKED`、`BASELINE_MISMATCH` 或 `REGRESSION`，不得硬压数量。
- 实现身份对比器如果需要新增 Python 代码，应作为**GPT 的 A 仓工作项**；Claude 可以负责提出 CI 接口要求、整理证据、适配不改核心行为的 workflow 配置（仍需批准）。

### 6.4 建议最小验收矩阵

| 项 | 平台 | 真实云端产物 | 判定 |
|---|---|---|---|
| 加载 + collect | GitHub Actions Windows | 完整 collection 摘要 | 不因配置/导入丢测试 |
| 动画 YAML 全链 smoke | GitHub Actions Windows | 用例日志、mock 产物摘要 | 明确测到各个实际存在的流水线阶段 |
| 全量 mock pytest | GitHub Actions Windows | JUnit XML + 失败身份差分 | 可复现，新增失败为 0 才具备“无新增回退”证据 |

## 9. 失败模式、停机条件与回滚策略

| 失败/风险 | 立即动作 | 可恢复方案 | 严格禁止 |
|---|---|---|---|
| PAT 无写工作流权限 / 管理权限 | STOP 相应操作，记录 HTTP 状态**不打印 token** | 网页由所有者完成对应设置；或用户另行核准最小权限 | 将 PAT 放 Git URL；盲目扩权 |
| Steam++/HTTPS 超时 | STOP，核对配置，先检查远端状态 | 保持 Steam++ 关闭；再验证 Git HTTPS；按需 Schannel/系统代理 | 盲目反复推/force |
| A 单推 2GiB / 网络中断 | STOP，检查 refs 与 GitHub 接收情况 | 真实历史小批迁移/恢复 push，校验 40 位 SHA | 删除 `.git`、`filter-repo`、伪造源快照 |
| C 存在敏感文件或 ZIP 内秘密 | 停止**公开**推送该批 | 本地排除/脱敏副本/用户审批后重做允许提交 | 先公开后指望简单删除即可抹除传播 |
| 父仓 gitlink 影响阅读 | 建立指针清单和 README | 后续普通 commit 移除第三方指针当前态，保留祖先 | 删除/重写父仓历史 |
| 依赖 lock 在 runner 安装失败 | CI 标 `INFRA_BLOCKED`，留日志 | GPT/批准的 CI 维护修依赖，重跑同平台 | 把未跑成功记为 PASS |
| 291 基线无法复现 | CI 标 `BASELINE_MISMATCH` | 找到原实际失败列表/环境重建 | 以失败总数粗略放行 |
| 测试出现真实外部 API 调用 | 立即停用相应云端 job | 改隔离策略及 mock 证据，重跑 | 配真 Agnes key 硬跑 |
| CI 配置后影响 main | 禁止无审查直接覆盖 | 对**新提交**用 PR / `git revert` 正常回滚 | force push/reset 旧历史 |
| Pages 配错或发布敏感路径 | 停止 Pages 发布并记录影响 | 修 Pages 源或撤回新增文件；公开披露按安全事件处理 | 宣称删除新 commit 能彻底收回已公开数据 |
| 删除后发现文件误失 | STOP 后续删除 | 从 Git 历史或 B/C SHA 校验副本、可选离线备份恢复；必要时 `git revert` 清理提交 | `git clean -fdx` / `git reset --hard` 草率恢复 |
| 用户审阅发现不应上传的历史内容 | **推送前 STOP** | 提交裁决：是否终止当前发布方案 | 违反禁止重写 A 历史的红线“悄悄修历史” |

**回滚原则**：移植后的原历史只能向前产生修复/撤销新改动的 commit，不删除既有历史。GitHub 公仓**已经公开的数据不能保证可被技术手段完全撤回**；所以公开内容审查必须发生在 push 之前。切换 Pages 设置不改变原 D 帧服务。每次关键操作要保存前后 `ref→SHA`、run URL、manifest 以及批准记录。
