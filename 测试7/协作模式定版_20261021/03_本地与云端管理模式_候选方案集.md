# 03 本地与云端管理模式——候选方案集（供专业 agent 评审定夺）

> 本文件列出本地 5 种、云端 5 种管理模式的候选。02 文件是其中「云端 C1」的详细规格（用户已迭代过的领先候选）。**最终选型请专业 agent 按文末评审标准给出结论**；选定后本文件夹相应文档升格为定版规格。

## 第一部分：本地管理模式候选

### L1 单活跃项目制
- **规则**：本地只留「当前正在做的 1 个项目」的全量数据+最新报告+最新预览；其余全部归档
- **优**：最省空间、零清理心智、状态最清晰
- **劣**：跨项目对照（复用旧素材/参考旧片）不便；回改旧项目必须先取回
- **适用**：项目串行推进、很少回头改的用户习惯

### L2 最近 3 阶段制（用户原案）
- **规则**：本地保留最近 3 个阶段/批次的相关文件，更早的针对性上传清理
- **优**：近期返工零等待
- **劣**：「阶段」边界模糊（战役？项目？批次？）；数字 3 凭经验
- **适用**：阶段概念清晰、节奏稳定的流程

### L3 满 5 阶段批量上传清理制（用户原案）
- **规则**：攒满 5 阶段一次性上传+清理
- **优**：操作频次最低
- **劣**：本地膨胀无预警；批量上传撞网络黑窗时滞留
- **适用**：报告/文件体量小且网络稳定期

### L4 六份缓存对称制（与云端 C1 同构）
- **规则**：本地 workspace 与云端同一套 6 份容量+标记+刷写规则
- **优**：本地云端一套心智，规则文档只有一份
- **劣**：本地也要实现标记/刷写逻辑（或人工执行同流程）
- **适用**：追求全局一致性

### L5 容量上限制
- **规则**：本地项目区设容量上限（如 2GB），超限按最近活跃时间刷最老的
- **优**：直接对准真实约束（磁盘/内存），体量自治
- **劣**：需要统计工具辅助；对用户不直观（不知道哪天轮到谁被刷）
- **适用**：项目体量波动大

## 第二部分：云端管理模式候选

### C1 A-workspace 六份缓存制（领先候选，详细规格见 02）
- **规则**：A 仓内 `workspace/` 过渡库存最新 6 份项目；超限标记最老；producer 空闲时刷入 B 深库；核验后释放；取回项目重占坑+3 天时限
- **优**：出生与存储同仓、流程直观、用户已深度迭代、与本地 L4 同构
- **劣**：A 仓体积随项目增长（有界 ≤6 份，约百 MB~GB 级）；CI 需处理 workspace（稀疏检出或接受略慢）；代码仓混数据（用户已接受此放宽）

### C2 B1 活跃工作区制（A 保持纯代码）
- **规则**：A 只放代码+tools；B1 作活跃项目仓（热），云端会话从 B1 拉、往 B1 写；B 深库收完结项目
- **优**：A 最纯净、CI 克隆最快；冷热彻底分离
- **劣**：多一仓一跳——产出「出生在 A 工作区」后要多一步推 B1；仓多一个心智
- **适用**：坚持代码仓零数据纪律的取向

### C3 即用即弃制
- **规则**：无活跃缓存——会话开始现从 B 拉指定项目包 → 跑 → 成果直接推 B
- **优**：最简心智、无缓存状态要维护、随时换机器零包袱
- **劣**：每次会话付全量拉取成本；中断恢复要求 B 上有细粒度提交（要做分步 checkpoint）
- **适用**：项目体量小、会话短频多

### C4 工件中转制
- **规则**：云端产出先存 Actions artifact（现保留 3 天）→ 定时归档 job 取回转存 B
- **优**：充分利用 Actions 原生能力，runner 侧零额外操作
- **劣**：下载→再上传两跳；定时 job 必须可靠（3 天窗口短）；artifact 有单文件 100MB 限制同源
- **适用**：产出物小、次数少的过渡期

### C5 双层缓存制（A workspace + B1 热镜像）
- **规则**：C1 基础上再加 B1 做活跃数据热镜像，双保险
- **优**：最稳（A 仓或 B1 任一故障可互救）、恢复能力最强
- **劣**：最复杂；双写一致性维护成本高
- **适用**：数据价值极高、不允许任何单点风险时

## 第三部分：评审标准（请专业 agent 逐项打分）

| 标准 | 含义 |
|---|---|
| 会话内速度 | agent 对话时的读写延迟（应全部=本地磁盘） |
| 同步成本 | 会话首尾一次性传输的体量与耗时 |
| 丢失窗口 | 最坏情况下可能丢多少未归档工作 |
| 实现复杂度 | 需要新写的能力/脚本数量 |
| 网络黑窗容忍 | 像本机这样时好时坏的网络下的韧性 |
| A 仓纯净度 | 代码仓是否被数据污染（影响 CI 与协作观感） |
| 与既有纪律契合 | master_lease 写锁/SHA256 审计/随做随清等现行规矩的兼容度 |

## 执行侧 Claude 的排序意见（仅供参考，定夺权在专业 agent 与用户）

- **云端**：C1 首选（用户已深度迭代、复杂度适中）→ 若 A 纯净权重最高则 C2 → C3 适合作为 C1 未建成前的过渡
- **本地**：L4（与云端同构）或 L1（最简起步，先跑起来再进化到 L4）
- **淘汰候选**：C4（两跳且窗口紧）、C5（过度设计，除非数据价值评估改变）
