# Phase 53 A｜现有模式的效率与协作测试

## 目的

用不同剧情给现有协作模式建立可复算的新基线，回答：慢在哪里、哪些等待有必要、哪些交接没有带来有效成果、失败后是否能保留已有成果。本批只测试，不修生产实现。

## A0：核验及冻结

先阅读仓库 `AGENTS.md`、当前正式注册、最新有效报告和实际入口。不要仅因历史文件名被提到就假设其内容已取得。记录报告真实路径；没有报告或源日志就标记“未取得”，不得编造统计。

核验并记录：

- 代码 commit、现存 diff 的哈希、依赖和运行环境。
- 六个 Agent 的准确 ID、职责、工具和 ownership；现有视觉审核的实际执行者/模型/输入。
- 正式 Skill 的路径、版本、正文哈希、registry/binding、被测入口的实际加载机制。
- 全部模型 ID、Provider/adapter、真实出站参数、Thinking、当前免费标记、可用配额及限流来源。只需核验实验相关路径，不重新做全行业调研。
- 审核维度、自动放行条件、用户 gate、修复上限、正式选片及 final render 的权限。
- 引用资产、裁切、尾帧提取、复用和恢复的真实机制。
- 日志能否保存 task ID、VideoVersion、提交/完成/收货/审核时间；客户端显示累计时间不能冒充单镜请求耗时。

保留当前生产 worktree 和用户改动。另建独立测试项目与输出目录；隔离配置和数据，不用 `reset` 清理用户仓库。记录开始时仓库状态，结束时确认正式代码和 Skill 没有新增差异。允许在测试目录写数据整理工具，不提交生产修改。

日志不足时，优先用现有事件、receipt 和客户端 trace 汇合取证。新增测试侧采集只能读取现有接口并记录观察时刻，不能修改生产源码；观察到的 Provider 完成时刻只是上界/区间，不是精确完成时间。

采集优先读取已有日志。额外轮询或文本总结会占用调用和限流预算，若确需增加，A/B 使用相同采集方式并记录其开销；不要用更密的 B 轮询制造“更早完成”的表象。

## A1：三个探索基线

采用 [剧情说明](PHASE53_03_STORY_SCENARIOS.md) 的室内、要塞、怪物故事，各自开全新系统会话和独立项目。让系统 Agent 自主写剧情、做资源、规划和生成，不把测试者预想的逐镜技术答案送进去。

按当前正式模式完整推进到可审片候选。素材审批及最终选片遵循现有 gate；用户尚未回复时，保存状态并继续其他已就绪的独立工作，不轮询式反复向用户确认。

每部保留：首次候选、机器判定、修复轨迹、最终所用版本、剪辑区间、原生音频、成片、用户意见与正式选择状态。不得只保留最好的一次。

三种题材难度不同，只用于观察各自瓶颈；不能直接用“室内比要塞快”证明协作模式优劣。探索基线不与复用其准备成果的 B 运行直接比较总耗时。

## A2：效率口径

| 指标 | 明确定义 |
| --- | --- |
| 冷启动总历时 | 从首次正式生产任务启动，到符合既有机器 gate 的完整候选可播放；含资源准备和必要中间人工等待 |
| 用户接受历时 | 从同一启动点到用户明确接受成片；尚未接受则保留未完成/待评状态及观察截止时刻 |
| 就绪生产历时 | 从共同比较快照的全部前置条件就绪，到完整候选可审；主要用于 B 配对 |
| 人工阻塞 | 真正因必要人工 gate 无法推进的区间并集；同时存在其他工作时不可全算关键路径等待 |
| 人工劳动 | 有证据的用户审片/操作时段；没有活动日志则写未测，不能用 waiting_human 代替 |
| Agent 交接延迟 | 接收方所有前置条件就绪后，到接收方实际开始工作的间隔 |
| 就绪至提交 | 某项媒体输入、版本、审核和依赖全部就绪，到出站提交请求开始 |
| Provider 可见耗时 | 请求提交/服务端接收至完成；缺精确服务端完成事件时给轮询观察区间 |
| 收货延迟 | 可核验的完成到正式资产入库、版本建立；缺事件则标未知 |
| 返工与复用 | 每镜全部候选数、失败原因、最终选择；同版本复用、stale 拒绝及重复生成分开计数 |
| 协作负担 | 委派/交回次数、重复读同一状态、工具调用、可取得的 input/output/cache tokens、压缩和接续失败 |
| 人工介入 | 例行审片和系统故障补救分开；Claude Code 补交/改分镜/补写 canonical 是救援，不能计自主成功 |

`t_ready` 必须取实际所需前置版本和 gate 全部满足的时刻，不能用“导演已经想好了”推定。多个并行任务的耗时不得直接相加成一部片的总历时。

必须分别交原始区间及互斥的墙钟时间线。若重叠原因难以判定，记 `mixed/unknown`。只有事件证明“可执行、无前置阻塞、却未推进”时才标空转；读状态、校验和审核可能有必要，不能自动视作浪费。

可附“总历时减人工阻塞并集”的描述性指标，同时保留原始总历时。该减法不能证明取消人审后真实会节省同样时间。

## A3：恢复与协作边界

在测试夹具或现有 fault-injection 入口做下列演练；复用既有媒体和回执即可，注明是回放/模拟，不能冒充真机生成成功。不要为故障测试重复支付生成额度。

1. 媒体提交已取得 task ID 后中断测试会话：恢复应优先查询与收货，已有成果不丢。
2. 提交结果不明：必须先对账；若无幂等或请求查找能力，就保留不确定状态，不能直接重发后宣称无重复。
3. 轮询失败/文本限流：任务仍在途，分类等待，检查是否拖住其他已就绪操作。
4. 合格同版本资产已有：若正式契约允许复用，完成判定应承认它；缺什么只补什么。
5. 上游已选版本改变：真实依赖的下游进入 freshness 复核；不能靠复用旧尾帧抢时间。
6. 重复/晚到回执：不能双重收货，旧结果不能覆盖新的已选版本。

若没有合法注入入口，就做日志回放和静态核验，标明“恢复行为未真机验证”。本轮不为覆盖这六项新建恢复框架。

## A4：问题归因与交付

每个异常写：事件链、实际影响、可排除的原因、尚未证明的假设。优先区分：业务决策、Agent 交接/上下文、工具或权限、排队限流、Provider 生成、审查误判、必要人工等待、模型画面错误。

请求正确但模型给出坏画面，说明生成候选失败；仍可统计系统是否及时发现、局部修复或停止。不能据此自动宣称协作失败，也不能把模型失败从成片效率中删掉。

提交 `PHASE53_A_EFFICIENCY_BASELINE_REPORT.md`，按三部片分别列原始数据、分段历时、失败与救援。最后给出最值得后续验证的流程改变及其证据，不在此批实现。
