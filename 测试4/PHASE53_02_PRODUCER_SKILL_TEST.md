# Phase 53 B｜Producer 直接加载 Skill 的独立对照

## 假设与真正的变量

假设：已批准计划中的例行制作，如果由 Producer 加载相应 Skill 并调用正式工具，可以减少“委派—重新读项目—说明进度—交回”的开销，同时保留质量和状态可靠性。也可能因角色规则叠加、上下文变长、误用工具而变慢。本实验不预先判胜。

模式 A：当前验收基线，沿实际协作路径委派专业 Agent；不人为改成每镜都走六员链。

模式 B：专业角色及职责继续存在，Producer 对白名单操作直接加载对应 Skill、实际执行。复杂创作、例外诊断和既有独立审核仍按原路径交回专业能力。两者唯一变化是执行主体/交接路线及实现它所必需的测试专用授权；生成策略、Skill 正文、模型、并发、检查及返工政策相同。

## B0：先确认这里的 Skill 属于哪层

被测对象是项目系统 Producer，不是外部 Claude Code 主会话。Claude Code 的 `/skill` 或 Skill 工具可作为客户端机制参考，不能替代项目 registry/binding 中的真实加载。

官方文档说明：Skill 提供可加载的规则；`context: fork` 会转入 subagent。Skill 在同一会话加载后可能继续占据上下文，因此“切换”不能被当作自动卸载旧规则。客户端工具许可也不等于项目 canonical 的业务写入授权。

必须记录：Claude Code 版本/会话类型、项目运行时版本、Skill 真实类型与实际执行主体。某些 subagent 继承上下文，另一些从独立定义起步；以本次版本、配置和 trace 为准，不假设所有 Agent 都采用同一隔离方式。

来源：[Skills](https://code.claude.com/docs/en/skills)、[Subagents](https://code.claude.com/docs/en/sub-agents)。这些客户端资料仅支持机制解释，不证明本项目已经拥有对应功能。

## B1：扩权范围

建立一张实际能力表，填准确工具和 Skill ID，不使用下列逻辑称呼伪造注册项。

| 逻辑操作 | B 默认可直接执行的范围 | 仍需遵守的条件 |
| --- | --- | --- |
| 项目状态与准备 | 读取 canonical、批准资源、依赖、版本；构建已有计划的执行清单 | 不改故事事实或批准状态 |
| 首帧/分镜图 | 加载当前正式制作 Skill，按已批准拍摄单生成和保存候选 | 与 A 相同参考绑定、模型和审核 |
| 视频生产 | 执行已批准镜头，提交、查询、收货、提取合格裁切端点 | 保留 task ID、真实请求、版本和依赖 |
| 局部返工 | 在当前明确规则及返工上限内产生新候选 | 不靠删关键动作或改剧情回避失败 |
| 成片 | 加载装配规则，按允许装配的同一选版清单产出候选 render | 不冒充用户 final_render 选择 |
| 复杂问题 | 委派导演/资源/场景等专业能力 | 记录委派缘由及专业产物 |
| 审核与最终接受 | 沿当前审核路径及人工 gate | Producer 不自行跳 gate 或自我批准 |

这是真正的操作授权实验，不能把每个“直接执行”又包装成一次完整专业 Agent 委派后仍声称交接已省。若 Skill 自带 fork、系统工具固定委派给导演，记为隐式委派；可保留作观察，但不算同主体直接操作。

canonical 若有固定 owner，必须通过后端现有的、可审计的授权能力明确允许测试 Producer 对对应对象/操作执行。记录实际 actor=Producer、逻辑业务职责、grant 来源与有效项目/会话，不冒充 Director，不伪造 owner。不支持授权的操作留为受阻，不能用管理员、直接 REST 或写数据库越过去。

批准现有测试范围的启动、调用和生成已在用户任务中给出，无须每切一个 Skill 都询问用户。系统本来要求的素材/选片 gate 仍须完成。

## B2：无媒体生成的能力探针

先在测试会话做读取、Skill 加载、请求编译/dry-run（存在时）、权限和候选输出路径核验。确认 Producer 真能拿到工具、后端真接受授权、回执记录主体正确。

测试用授权/config/profile 只使用现有支持方式，并保存差异和撤销方法。不得改正式 Skill 去除限制，或给全局开启权限绕过。当前能力不足时，提交 `BLOCKED_CAPABILITY`，指出需要的最小后续实现；继续 A 批。允许另外报告已经可执行的子集，称 `B_PARTIAL`，不能冒充完整 B。

探针检查：

- Skill 加载的真实路径、版本、哈希与时刻；只说“已加载”不算证据。
- 提交前能按现有契约核验输入/版本及模式；加载与执行之间没有隐藏的人类或外部 Agent 补操作。
- 制作 Skill 与装配 Skill 连续加载后，当前职责及适用规则是否清楚；有冲突时报告并停止该操作，不改原文来得到通过。
- 专业审核仍由既有审核路径完成；若路径与生产主体共享上下文，记录其独立性限制，不能写成独立盲审。
- 当前分镜图缺少资源、错版本、错端点时，Producer 会正确阻塞/交回，而非自行扩权绕过。

## B3：冻结共同工作包

以室内剧情为主试验。A 批探索完成准备后，冻结已批准剧本、六镜拍摄单、角色 Look、茶杯/标本/室内资源、声音策略及逐镜生成目标。不要把探索基线的成功源视频提供给“新生成”槽。

A、B 各克隆同一批准快照；起跑前全部准备条件一致。两组都重新生成所测的分镜图和视频候选，不能一组复用另一组输出。输出 namespace、会话记忆、任务表和候选完全隔离；共同批准输入只读复制，核验内容哈希一致。

克隆时只保留批准故事、拍摄单及参考资源。清除克隆测试项目中被测分镜图/视频的输出引用、选版指针、审核完成状态及相关运行状态，检查没有被继承的“已完成”标记；原项目和源媒体保留。记录平台跨项目去重/缓存政策，并使 A/B 相同；如果无法确保所测素材确为新请求，就另标复用实验，不能混入新生成耗时。

这一比较是“输入就绪后的制作—审核—装配效率”，不包含新编剧和新资源创作的冷启动收益。将它冒充全流程提速属于误报。A 批冷启动指标另列。

## B4：配对执行

先做区组 1：A→B；条件不变再做区组 2：B→A、区组 3：A→B。每次新会话、独立克隆项目。同区组尽量相邻排期，记录日期/时段、已知服务异常和客户端/模型变化；两个模式同时抢同一限流池会引入干扰，默认不同时生成。

保持相同剧情、拍摄单、批准图像内容、模型与请求约束、源时长、成片目标、在途上限、轮询策略、自动审核、修复上限、用户 gate。平台有可用 seed 时同区组记录并一致设置；没有 seed 就接受随机性并重复，不能自造种子字段。

允许 A、B 的 Agent 在相同 Skill 规则范围内自行判断，不给 B 逐镜答案，也不对 A 刻意增加确认。实际选择路径不同，记录成中介变量，不能再断言全是交接开销；可用相同事件回放辅助解释纯调度差异，但回放不代替真机质量和耗时结果。

任何版本/政策改变，都使后续样本进入新批次；首个区组失败也保留。若权限探针只支持部分白名单，先固定该子集再比较，并明确未测试范围。

## B5：评价与采用条件

先核验相同负荷和质量门槛，再比较：每部的交接间隔、就绪至提交、就绪生产历时、人工补救、总请求/候选/额度、tokens 与上下文压缩。所有失败或中途终止保留在成功率分母；速度统计只对双方均完成且质量可比较的配对给出，并同时披露删去哪些区组及原因。

以一个完整运行/配对区组为单位，不能把同片多个互相依赖的镜头当独立样本。报告每个区组的原始值与配对差值；描述中位差异，不凭三个区组宣称统计显著或长期可靠。未完成者报告观察截止时间和原因，不用零秒或最好候选替代。

测试前把“是否值得下一阶段继续验证”的参考目标写入预登记：例如就绪生产历时的配对中位数至少减少百分之十五，审核硬错误、故障补救和生成消耗没有观察到增加。这个值是本轮工程目标，不是行业标准，也不能用小样本证明质量非劣。未达到目标仍如实记录交接是否减少。

可建议继续验证 B 的条件：完整可执行、共同负荷满足、真实授权可审计、用户未发现新增硬错误、恢复没有新增风险，且耗时/投入有一致改善线索。只有交接变少而成片时间不变，应写“协调开销下降，端到端收益未证实”。更快但常自我批准/漏审/改故事，应判不可采用。

## B6：可选扩展，另行编号

若默认 B 可行，进一步允许 Producer 直接调用编剧、资源、场景 Skill 产出草稿或候选，可另记 `B_PLUS`。需要现有正式工具、同样可审计的 scoped grant 和新冷启动配对；业务对象 owner、专业审核和用户批准仍保留。它改变了更多职责，不能混入默认 B 的统计。

要塞和怪物各补一个 A/B 配对，可观察是否只在简单室内受益。不要同时改变角色数、时长或视频模式。新调度并发策略也另建实验，不和扩权一起改。
