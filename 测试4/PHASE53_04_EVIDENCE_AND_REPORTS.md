# Phase 53｜证据、复算与报告模板

## 最少取证，足够解释

优先导出已有账本和 trace，不建立新的复杂可观测平台。日志不得保存 key/token 或完整敏感签名 URL；请求里保留模式、字段、资产 ID、内容哈希和可取证引用即可。

每个运行必须可关联到：`run_id`、题材、A/B/B_PARTIAL/B_PLUS、配对区组、会话和项目 ID、代码/Skill/模型/config/输入快照标识、开始/结束或截止时刻、状态、人工介入与输出文件。

最低证据集：

- `runs.csv`：一个运行一行，所有启动、失败、中断和待评都保留。
- `events.jsonl`：既有事件的规范化导出；保留原日志引用和时钟来源，不假装这些字段是现有 API。
- `media_tasks.csv`：每项提交、task ID、Provider 状态、正式资产/版本、选用/弃用/失败及额度。
- `skill_loads.jsonl`：实际 actor、Skill 路径/版本/哈希、加载方式、对应动作；没有加载事件用可核验 trace 引用，不补写成事前事件。
- `reviews.csv`：哪个版本/裁切区间由谁在何时审查，判断与理由，用户状态另列。
- `interventions.csv`：人或 Claude Code 做了什么、原因、起止、是否改变实验。
- `input_manifest.json`、`candidate_config_diff`、`evidence_index.md`，以及完整可播放成片、源镜、关键帧和保留的失败样本。

字段欠缺可标 `null/unknown`，不能填零。测试侧观察事件加 `observed_at` 和 `derived=true`；事后推导与真实当时事件分开。

## 事件时间线

每条事件可规范化为：事件 ID、run/task/object/version ID、actor、逻辑职责、event type、UTC timestamp、单进程 monotonic 时刻（有则保留）、时钟来源、原始日志引用、已满足/未满足依赖、原因。

跨进程不用单进程 monotonic 直接相减。核对 wall clock 偏移，不确定则标区间。服务端完成事件、客户端第一次观察完成、资产入库是不同事件。

对同一逻辑生成请求保留 request/idempotency/task 的对应关系。通过唯一 task ID 和产物版本对账成功任务数；重复导出和重复回调不增加生成次数。先定义计数对象：请求、视频任务、候选版本、已选镜头、审查次数，不能相互替代。

晚到结果与旧版本都保留，是否可选择由正式 freshness 和 owner 规则决定。确实存在产物但缺少原始任务记录时标 provenance 缺口，不凭文件名推断所有过程。

## Python 复算要求

Claude Code 应在本地用 Python 对真实数据复算，并随报告交计算工具、输入文件、命令和输出。

1. 用唯一任务 ID 和版本关联核对汇总。逐项解释差异，不把旧报告的数字强行写入新账本。
2. `ready_to_submit = submit_started - ready_at`，其中 ready_at 是全部实际前置/gate 就绪的最晚时刻。出现负值须查时钟/事件/版本，不能自动取绝对值。
3. 从单请求 submit 到 completed 计算 Provider 可见耗时。若完成只经轮询发现，给最后未完成观察与首次完成观察形成的区间；第一次轮询就是完成时，区间下界只能来自可信接收时刻。
4. 人工/等待/运行区间先合并并裁到该 run 的观察窗，再汇总。检查区间长度为零、重叠、相邻、越界、缺终点、跨重启和多 gate。
5. 对一片内并行节点建立依赖时间线，不能把每个节点的 provider 时长和人审时长相加成总历时。
6. 分别报告原始历时、人工阻塞并集、已知交接与工具开销、unknown；若互斥分类成立，反算类别之和须等于观察窗长度。
7. 配对节省比例采用 `(A - B) / A`。A 为零或缺失时给未定义。保留每个配对值；中位数使用配对改善比例或配对差值，并注明定义，不把组均值之比冒充配对结果。
8. 先报告所有运行的完成/失败/待评计数，再描述双方完成且负荷一致的速度子集。任一组失败不能静默删除。
9. tokens 缺测则写缺测；input/output/cache 分列，不重复相加已包含 cache 的总量。免费额度不代表没有消耗。

不要基于三个配对运行给 p95 或显著性结论；可报告各轮原始数据、范围和中位数，写成探索证据。镜头粒度的样本可用于定位问题，不能作为独立影片样本扩大统计信心。

## A 报告模板

`PHASE53_A_EFFICIENCY_BASELINE_REPORT.md`

1. 当前真实基线及无法核验项。
2. 三种故事的工作负荷、批准输入和成片链接。
3. 每部完整时间线、失败/候选/人工介入、自动与用户评审状态。
4. 已证实损耗：发生在何处、多久、影响哪些结果、原始证据。
5. 模型画面失败与系统推进失败的区分；复用、恢复和限流观察。
6. 后续建议：按证据和可检验收益排序，本轮没有实施的建议明确写未实施。

## B 报告模板

`PHASE53_B_PRODUCER_SKILL_SWITCH_REPORT.md`

1. A/B 差异与权限表：真实 actor、业务授权、直接/隐式委派、不能执行项。
2. Skill 真实加载与连续切换轨迹；旧规则残留、压缩、工具误用。
3. 预登记：共同快照、固定变量、配对次序、预算、目标、停止条件。
4. 各区组的运行、产物、评审和耗时；全部失败与救援。
5. 配对对照表：就绪生产历时、交接间隔、提交延迟、生成/返工、tokens、人工。
6. 恢复与权限边界；生成回放不冒充真机证据。
7. 支持继续验证 / 仅部分可行 / 无明显收益 / 不可执行或不可采用，并写适用范围。

配对表至少包括：区组、A/B run_id、负荷一致性、完成状态、机器 gate、用户状态、A/B 原始历时、配对差值及比例、候选数、救援、混杂因素。尚待用户看片的结论写暂定。

## C 汇总模板

`PHASE53_C_SYNTHESIS_AND_NEXT_STEPS.md`

分别回答：

- 六员体系能否完成这批任务？
- 当前效率瓶颈在哪里，是否有确切空转证据？
- Producer 直接执行真的可行吗？是否减少了交接？是否更快交出同门槛的片子？
- 收益是否只在室内/固定输入成立？复杂故事、冷启动和长期连续使用哪些未测？
- 哪些方法保留，哪些只建议下一阶段验证，哪些不采用？

不要把“没有新增故障”“流程可用”“速度目标达成”“用户满意”合成一个 PASS。不宣布系统没有问题或协作已最优。

## 停止、配额与撤销

先处理已有在途任务及其 ID，再结束运行；测试配置只在相关任务妥善结算后撤销。提交结果不明时不得重复补交。

遇到正式权限无法满足、引用错误端点、关键输入不合法、免费主链不可用或配额耗尽，按明确原因停止相关生成。继续日志核验、恢复回放和报告；不要为了完成表格换付费模型、绕过 gate 或删失败样本。

自动放行/修复上限的既有触发条件到了就停止该镜并报告，不扩大返工以追求漂亮成片。测试涉及的图片、视频和返工预算在预登记中逐项列出，逐批对账。

最后确认：正式代码/Skill/全局权限与开始相比没有本轮新增改动；临时授权已撤销；用户原有改动仍保留；测试证据和候选可读取。不要删除任务、历史回执或失败产物。
