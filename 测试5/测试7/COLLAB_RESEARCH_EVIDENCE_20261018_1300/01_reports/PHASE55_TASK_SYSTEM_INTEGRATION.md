日期：2026-10-17。用途：交给能访问真实项目仓库的 Claude Code 实施。

本文件是下一阶段执行任务书，不是已经完成的系统改造报告。依据本次提供的 `PHASE54_REPORT.md`；报告所述源码、日志、视频及其它报告，仍须在项目仓库逐项核验。当前写作环境没有这些项目文件。

## 1. 阶段判断

现在可以从“继续比短片效果”转向“把可选协作方案和并发能力真正纳入系统”。保留六员体系、scoped grant、canonical、OCC、receipts 和现有工作流，补齐共同执行基础，再让用户方便选择和测试。

本阶段主要验收工程行为：任务是否及时推进、依赖是否正确、参考链是否完整、并发是否真实、恢复是否可靠、模式是否可复现。画面仍做基本检查和有限修复；不以当前视频模型达到理想电影效果作为系统化收工条件，不要求先重修所有旧片。

更好的模型值得接入和使用。参考漏传、错误选版、未知提交重复补交、会话溢出等仍是系统职责，应在本轮处理，避免换模型后重复暴露。

### 报告能支持什么

- Producer 扩权和直接执行已有真实运行依据，可以工程化为正式可配置能力。
- 预铺、困难上交与会话接力均有可复用经验，不必每次靠执行侧临时拼接。
- 模式之间存在明显耗时差异，但参考绑定、审核和修复也一起变了；当前数据是观察证据，不能把全部速度差都归因于执行架构。
- 场景参考链缺失是优先排查和统一的输入缺口。报告尚未严格证明“只有场景图能维持场景”或“强制场景图是唯一不可替代来源”；M6 的执行侧与用户结论也提醒我们，参考传入不等于接缝必然合格。

因此，本轮采用的工程规则是：**切换协作模式不应静默改变已选的生成契约、参考策略和验收要求。** 先保持原六员基线的有效输入链可复现，后续再单独比较参考策略。

## 2. 授权范围与实施原则

本轮允许修改后端、必要的前端运行配置、定向测试、文档和正式加载/绑定接线；这是工程实施阶段，已不受上一轮“仅测试、不改生产代码”的范围约束。

在独立分支或 worktree 实施，保留用户未提交改动。先读 `AGENTS.md` 和当前源码；报告提及的 `src/agents/grant.py`、`routers/agents.py`、`shot.generate_videos` 等均核验真实位置，不照抄路径造新架构。尽量复用已有任务、锁、队列、恢复和工作流能力。

不新增一套项目事实存储，不把 Agent 聊天当真相，不移除 owner/OCC，不靠管理员或数据库直写绕过授权。无需为本任务引入 LangGraph、Langflow 后端、分布式集群或消息中间件；若现有栈足以做异步调度，就在原栈完成。

模型输出能力与基础设施验收分开。使用当前实际可用的授权模型和额度，记录真实 ID、adapter、请求与 Thinking；不暗中更换模型制造提速，不因遇到失败自动换收费模型。

用户已授权本轮工程实现和范围内测试。按现有规则处理必要的人审、最终选片及定版；不为每个普通修改、Skill 切换或测试启动重复请求确认。

## 3. 先定义共同执行基础

所有协作预设共用：

1. 同一模型能力校验与请求编译入口。
2. 同一资源/场景/人数约束绑定规则及输入依据记录。
3. 同一持久任务账本、依赖判定、幂等收货和候选版本机制。
4. 可独立配置、版本化的审核/修复政策。
5. 同一统计口径和证据导出。

然后在上面改变“谁规划、谁执行、何时委派、哪些任务可并行”。不要为每个模式复制一套生成代码。

### 统一参考链与生成契约：本轮优先级最高的前置

查明六员 BOUND 路径如何把 sciv、人物 Look、状态/人数约束送入真正生成链；对照 Producer 的同类工具调用，定位默认值、binding、编译或参数传递差异。

每个生成任务保留一份输入依据清单，至少包含：故事/镜头版本、方法、角色/场景/道具资产与版本、使用目的、起止状态、上游已选版本和实际裁切端点、人数规则、实际 adapter 请求模式。实际命名适配原有 schema。

场景图可以是视频原生 reference，也可以先进入首帧制作，再由首帧进入视频；必须能追溯资产→绑定→真实输入。图片准备好了却只在 prompt 中提到，不算已经传图。若模型模式互斥或槽位不够，按能力选择合法路线，不能强塞不支持的“首帧+额外参考”，也不能静默丢掉必需资产。

默认采用已验证的基线等价策略，要求同一镜头在不同角色/模式下生成相同意图的合法请求。需要探索“少参考/不同参考”的实验预设可以注册，但应显式标注，不与协作模式对照混算。

将 M5 的 `negative_prompt` 事故纳入编译校验：项目层意图应由模型能力层编译成合法字段或正文约束。未知字段、互斥字段和不合法时长在提交前明确报错，不让全部视频排队后才一起失败。不要用执行侧批量清库改字段作为常规解法。

保留 Phase54 的 `repairRequireNew` 和终审卡 refresh 语义：修复 attempt 必须有目标镜本 attempt 的新成果；已决策卡不可换内容后继续沿用旧决定。

## 4. 协作模式注册与组合

模式是声明式运行配置，不是新 Agent 类别。准确角色 ID 由当前注册表映射。

| 预设 | 执行方式 | 保留价值 | 适用限制 |
| --- | --- | --- | --- |
| 六员协作 | 按已有专业分工委派 | 质量基线、职责清楚、便于回归 | 不强制每个动作都完整遍历六员 |
| Producer 主执行 | scoped grant 后直接加载相应 Skill 并调用正式工具 | 少交接、适合计划已明确的例行制作 | 必须具备会话接力和共用审核 |
| 专业预铺+主执行 | 需要的角色/资源与场景任务在依赖允许时并行准备，之后主执行 | 保留专业素材能力 | 先有稳定制作简报/故事依据，避免泛做大量无用素材 |
| 主执行+困难上交 | Producer 主执行，明确困难按职责交回 | 减少常规委派，保留专业兜底 | 不能把“未上交”当作质量或鲁棒性证明 |
| 组合预设 | 引用上述策略：预铺+主执行+上交+独立审核 | 方便直接复测报告推荐组合 | 不复制另一套工具、参考或状态实现 |

预设内可分别选择：执行/上交策略、预铺范围、并发配置、参考策略、审核修复政策、会话接力政策。它们有合法组合约束，不能简单提供任意排列却不校验。

### 最小配置契约

建议保留或映射：模式 ID/版本、角色策略、预铺规则、上交条件、允许工具 families、并发 profile、参考/审核/修复/context policy 版本、能力要求和实验标识。这里是逻辑契约，不要求硬搬字段名。

run 启动时固定全部配置、模型及 Skill 版本，输出快照哈希。修改预设只影响后续 run。在途运行若需要迁移，显式迁移并记录兼容性；不能静默用新规则恢复旧运行。

所有预设应能经产品正常入口启动，不能只有执行侧 REST 脚本能运行。尚未具备能力的预设标记不可用并给具体原因，不能用演示成功替代。

上交包括明确任务、输入版本、所需专业产物和完成判定；返回轻量引用，避免完整聊天往返复制。错误分类至少区分参数/输入问题、模型拒绝、资源缺失、OCC 冲突、审核驳回和真正需要专业判断的问题。

内容策略拒绝按真实原因停下或走合规替代并记录变更；预检用于减少无效调用，不设计绕过 Provider 内容策略的方法。

## 5. 多线程的实际实施：异步在途+按依赖推进

优先做异步任务调度和必要的专业并行。不要先让多个 Producer 同时改同一项目。一个项目保留一个主控写入者，媒体任务和独立专业任务可以并行。

### 可并行与必须等待

| 工作 | 可以何时并行 | 必须满足什么 |
| --- | --- | --- |
| 角色资源与场景准备 | 稳定简报/故事依据已具备，目标对象不冲突 | 正确版本与 ownership；不先建错实例再补救 |
| 多个分镜图/视频 | 各自所有输入已批准、就绪且相互无真实媒体依赖 | 共同参考策略、容量与额度许可 |
| 连续尾帧链 | 不同独立链可并行 | 链内下一镜等上镜所需审核/选版/实际端点就绪 |
| 已完成视频的审查与其他生成 | 独立资产、独立计算额度允许时 | 审查精确绑定版本/区间，不能只审首帧 |
| 局部修复与其它分支 | 不影响其他分支输入时 | 受影响下游按真实依赖阻塞/过期 |
| 装配 | 所需选版及 gate 已齐备 | 固定清单；未审全片可预览但不能冒充正式通过 |

### 就绪队列与推进机制

从已批准生产计划建立/投影依赖图，不新造第二份 canonical。节点因依赖、审批、额度或资源锁阻塞时显示具体原因。只派发全部前置条件成立的任务。

采用事件驱动的就绪队列：任一任务收货或 gate 完成后，只唤醒受影响下游；有容量立即推进其它 ready 任务。避免“同一批全部完成才开始下一批”的无必要全局屏障。批处理可用于提交效率，不改变真实依赖语义。

计划、输入绑定、合法参数已经固定的例行步骤，交确定性执行器推进。不要每轮轮询都要求 Producer 再读全项目、解释进度、确认提交；只有决策、异常或阶段结果需要模型介入。

先以单项目媒体在途上限 1 为回归基线，再在实际配额允许时逐级试 2、3。报告称已有 outstanding=3 实证，实施侧先核验对应任务时间重叠和账户；它不是所有账户、端点或多项目均可无限并发的证明。

### 三种容量分别管理

- Agent/文本/视觉调用的并发上限。
- 图片/视频在途任务上限。
- 按真实账号/Provider 限流组共享的请求频率、token/每日秒数等预算。

不要假设 text、vision、poll、image、video 一定各有独立池。跨项目共享同一账户时容量也必须全局计数；单项目上限还要受账户总上限约束。轮询占用的请求预算纳入同一真实限流组。

本轮先支持可配置的固定上限、背压和有界退避。429 等按实际 Retry-After/规则处理，不立即爆发重试；“自适应调参”作为后续可选增强，不作为本轮可用的前提。

### 并发写入与资源锁

任务领取与容量预留必须原子化，避免两个调度回合重复领取同一生成。不同镜头可以并行生成候选；写共享项目索引、选版和聚合状态时沿用 OCC 或串行汇总，不能为了并发关闭冲突检查。

各 worker 返回版本化产物和回执引用。旧 revision 的结果可保存为候选，但不得覆盖新选择；结果到达时复核输入 basis 和 freshness。多个项目公平排期，失败/长任务不饿死其它 ready 任务。

## 6. 持久任务与休眠恢复

Provider 生成不能绑定在某一个 Agent turn 的存活期。提交、查询/通知、收货、审核、选版分开保存状态，Agent 会话重启不丢任务。

至少区分：待就绪、待容量、提交意图已记录、提交结果不明、已知 Provider 任务在途、收货待处理、待审/待选、成功、确定失败、取消待核验。可复用原有状态机，不强求新增同名枚举。

提交前持久化逻辑请求 ID、attempt、输入 basis 和预算预留；尽早保存 Provider task ID。Provider 有幂等键时沿用同一逻辑请求键；没有时如实承认网络断点下不能承诺端到端 exactly-once，以对账、去重收货和不盲目补交减少风险。

**本地机器休眠、心跳失联、轮询超时，不等于 Provider 任务已失败。** 重点审查报告 M5 “watchdog 作废卡死任务+自动补交”：

1. 有 task ID：恢复先查询原任务，成功则收货，在途则继续等待，确定失败才按政策新建 attempt。
2. 提交结果不明：先用请求/幂等/任务记录对账；不能证明未提交时保留 UNKNOWN，不能无条件补交。
3. 取消只能说明已请求取消时，不释放成可重用的全部预算/在途容量，等待实际状态确认。
4. 重复通知、轮询与晚到回执只登记一次正式收货；历史结果和费用仍保留。

短期可以采用原有持久存储加异步循环，不要求新服务器或分布式服务。若主机休眠，恢复后必须可正确续跑；“无人值守持续运行”是否还需要常驻主机，应作为部署条件单列，不能靠应用 watchdog 保证机器不休眠。

## 7. Producer 会话接力与授权

本轮把人工 session-split 变成正式机制，优先解决大工具面和长历史叠加的风险。

监控实际下一请求预算：系统提示、当前工具 schema、已加载 Skill、必要历史、图像/其它媒体预算，以及输出预留和安全余量。累计消费 tokens 另记成本，不能当作当前上下文长度。

阈值按真实模型/Provider 配置，不能硬编码报告的 467k/524k。先用已有压缩和工具结果裁剪；正文保留关键事实引用，长日志和媒体不反复塞回上下文。工具按当前任务需要分组暴露，但不得造成已获授权的必要工具在操作时突然不可用。

接近预算上限时：停止发起需要新推理的新动作，持久化交接点，启动新会话恢复；在途媒体由任务系统继续管理，不重发。

交接包至少包含：run/配置快照、canonical revision 和清单引用、已选资产及真实端点、未完成工作、所有在途/不明任务 ID、待审事项、已发生拒绝/失败、当前授权来源、下一项可做的操作。交接摘要是索引，新会话须回读真实状态，不把旧摘要当项目真相。

主控写入应有可核验的会话代次/租约或等价机制。新会话接管后，旧会话晚返回不能再次主控写入；合法的在途任务结果仍由当前授权收货路径处理。

grant 到期、撤销与交接不能互相打架：新会话按现有合法授权规则续期/重建 scoped grant，检查 project/families/TTL/actor；摘要里写了权限不等于获得权限。不得为免溢出或恢复直接改成全局永久授权。

## 8. 审核、选版与局部修复

本轮不继续扩大审美评分体系。把既有三查和已确认的一票否决项工具化、绑定版本，减少执行侧人工抽帧和卡片流转。

独立审核可以与其它独立生成重叠。复用现有视觉能力，固定输入 manifest 和裁切区间，保存抽帧位置、判断与证据；不新增业务角色来凑独立性。审核者若与制作共享上下文，明确标识，不能宣称完全独立盲审。

明确硬错误要进入有界局部修复/停止：不符合计划的额外人物、必需人物缺失、关键场景/动作结果错误、来源或版本无效。场景检查依据故事事实，不把正常切镜判为“必须逐帧相似”。“MINOR 不拦”不能吞掉已定义的硬错误。

用户提出这一阶段不纠结模型实际效果，应落实为：工程链路可以通过，候选画面仍可不通过；保留结果和缺陷，不为追求完美无限重生。仅审美不足、不影响本轮工程验证的项记录后继续，不阻塞所有工程工作。

模式对照使用同一个 review/repair profile。同一版本/同一区间/同一审核政策的有效结果可复用；媒体、裁切、参考状态或政策变了须复核。不得通过少审一组制造提速。

选版后生成固定装配清单：每镜实际选版、裁切、审核状态、上下游连接依据。允许按现有权限自主推荐候选，最终定版仍按原有授权。跨镜连续性不能只看每镜独立最高分；至少核对相邻镜的人物、地点和道具终态/初态。

局部返工只动错误镜及真实依赖；修复产生新候选，不能用 prior credit 冒充。审核卡刷新保留审计，已决策卡的内容不可原地改写。修复上限到达后如实结束该分支，继续不依赖它的工作。

可配置工程跑分时关闭或简化视觉环节，但必须另标“调度测试、非可交付候选”，不能和相同质量门槛的影片速度混在一起。

## 9. 产品入口：方便选择，便于复测

沿用现有 Agent、Skill、人工审核三种画布组件，不因本轮增加一堆新节点类型。优先新增运行级配置：

- 协作预设选择及简短用途说明。
- 并发档位与当前实际限额；超出账号可用能力时明确说明。
- 折叠的参考策略、审核/修复和上下文配置；默认使用验证基线。
- 运行时显示排队、在途、待审、阻塞原因、专业上交和会话接力状态。
- 复制本次配置、导出证据、用新项目复测。

画布和日志展示实际发生的委派与直接执行，不把所有模式都画成同一条虚假六员链。高级内部字段、schema 哈希和锁实现留在调试视图，普通制作流程只展示有助决策的信息。

## 10. 实施批次与推进顺序

### A｜核验与统一契约

交最短依据表：真实入口、六员/Skill/grant、BOUND 与 Producer 参考差异、调度状态、上下文计量、watchdog、审核及原始账本。优先复用当前已存在的实现。

修通共用绑定/编译/输入清单，保留 A2/A3 守卫；同一准备输入在不同模式下都经过同一有效路径。针对角色调用差异、缺场景图、非法字段、旧端点做定向验证。

### B｜预设注册与可用入口

把已有协作方法注册，支持组合预设和配置版本固定。先接通串行等价行为，能够从正常产品入口选择和运行。明确上交条件和回填产物，不复制生成逻辑。

### C｜有界并发与持久恢复

实现就绪队列、账号共享容量、依赖/锁、幂等收货、UNKNOWN 对账；先低并发验证，再逐级提升。在途任务不要求 Producer 持续轮询思考。

### D｜会话接力与审核流水化

补主控交接、预算监控、工具/结果精简、授权衔接。把独立审核和局部修复接到统一清单，减少手工抽帧和审核卡空转。

### E｜前端配置、基准与中长片压力测试

接产品可选项和真实运行状态；执行下一节测试。基础机制稳定后做更长作品的工程压力测试，不先扩大故事来掩盖参考链缺失。

这些是逻辑里程碑，实施者可按仓库依赖合并提交；每批交可检查结果，不应只完成注册表就宣称本阶段结束。普通实现问题自行处理并复验，只有需要用户视觉/剧情决定或超出授权范围时才提供具体材料。

## 11. 测试与验收

### 11.1 先做无媒体费用的工程验证

| 类别 | 必测情景 | 通过条件 |
| --- | --- | --- |
| 注册与固定配置 | 所有预设、组合、无效组合、运行中改配置 | 各走真实策略；在途快照不变；不支持的组合明确拒绝 |
| 参考链 | 同一镜头分别从专业 Agent 与 Producer 发起；场景缺失/过期/槽位受限 | 不静默降级；输入依据可追溯；合法请求等价 |
| 依赖 | 独立镜头、完整尾帧链、混合分支 | 独立任务能重叠；依赖镜头不会提前提交 |
| 容量 | 多项目共用账号、轮询与生成共池、429 | 不超过共享容量；背压可解释；无重试风暴 |
| 并发写 | 双重领取、冲突、乱序回调 | 不重复派发；OCC 生效；旧结果不覆盖新选版 |
| 恢复 | 提交前断点、已知 ID 中断、未知提交、休眠、取消未确认 | 查询/对账优先；不盲目补交；状态和额度诚实 |
| 会话 | 低阈值强制接力、旧会话晚返回、grant 过期 | 任务不丢、无双主写入、授权正确续接 |
| 审核修复 | 错人数、错场景、改裁切、旧卡刷新、prior credit | 守卫正确，有界返工，审核与版本对应 |

尽量用现有测试夹具、回放和假 Provider 完成故障注入，并明确哪些是模拟。模拟不证明真实平台接受并发。

对实际修改路径运行有意义的定向测试和项目要求的回归；全量旧环境失败保留准确失败集合与基线证据，不能只看失败总数一致。

### 11.2 真机验证分轴做

1. **接线冒烟**：每个预设通过正常入口真实完成至少一个最小任务。可使用共用批准资源，但被测请求/模式/actor/产物必须真实。合成回放或执行侧补交不计真实自主通过。
2. **并发收益主试验**：固定一个协作预设、同一批准输入、分镜、模型/参考/审核/时长，仅改变媒体在途上限。分别测 1、2、3，账号不支持则实测到合法上限。任务图同时包含独立分支和一条真实接续链。
3. **协作收益试验**：固定并发与其它政策，再比较六员、主执行、预铺、上交及组合。首轮为探索；出现收益的配置再重复配对，逐步积累，而非把所有配置做巨大笛卡尔积。
4. **恢复实战**：在真实任务已取得 ID 后中断客户端/受控重启，核对仅收货不重复生成。无法安全验证的故障只做回放并写明限制。

每个运行独立会话和项目输出，输入快照只读复制；被测新生成阶段不能继承基线视频及已完成标记。两组使用相同缓存/去重政策。配对尽量相邻排期、交替顺序，记录服务端异常、配额和人工介入。

### 11.3 中长片测试

基础工程通过后，按报告建议扩展到约二至四分钟的压力任务，观察任务排队、多个故事段、参考复用、上下文接力、局部修复和额度管理。必要时跨配额日恢复；先计算总源素材需求和当下额度，不把“免费”当作无限。

镜头数由批准剧情和当前模型可用素材时长决定。目标成片时长必须能由有效片段总和减转场重叠得到，不能固定少量镜头后承诺足够长。扩展故事也须有事件和结果，不能只是拉长空镜。

长片样本用于工程压力，不自动证明“短片太短导致衔接差”；故事、镜头数和时长同时变化时因果无法隔离。工程稳定后，如有价值再单测节奏/时长。

### 11.4 验收分开判定

工程可验收应满足：模式可选择且真实执行、输入链一致、有依赖的并发可证、持久恢复与接力通过、正常入口可用、回归范围清楚、失败与人工救援完整记录。当前模型画面未达到理想水准可以列为模型/制作边界，不因此把已完成的基础设施全部判失败。

同时，工程通过不自动等于候选可交付。保留机器审核与用户看片状态，既有硬错误不因本轮不纠结审美而改成 PASS。

并发成功需有真实在途重叠、容量记录和相同负荷下的耗时/吞吐证据。依赖链没有提速可以是正常结果，不用人为拆依赖证明“多线程有效”。不预先承诺翻倍或固定节省百分比。

## 13. 方法来源及适用边界

- [Anthropic：Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：压缩、外部结构化记录和按需取上下文。会话接力仍须核验项目事实和授权。

- 枚举五个任务、固定拓扑顺序下全部 1024 种前向有向无环图；以容量 1、2、3 共运行 3072 次合成调度，核对依赖、唯一执行、容量与串行总耗时。
