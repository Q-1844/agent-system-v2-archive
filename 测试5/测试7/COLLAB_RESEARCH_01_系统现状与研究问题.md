# 视频制作系统｜协作架构深度研究现状交接

日期：2026-10-18。供新对话的研究 Agent 使用。

## 1. 用户要什么

系统希望从故事目标出发，组织剧本、角色与场景资产、分镜、图像/视频生成、审核修复与剪辑装配。用户既需要 Agent 协作能力，也需要可配置的工作流；研究对象是现有产品的协作与执行结构。

当前首要目标有两个：**缩短单片从开工到可交付的等待时间，减少用户与 Claude Code 的人工推动。** 画面效果是附带观察。用户认为以后使用更好的模型会改善效果，因此不希望持续围绕个别画面进行无休止调参；但漏参考、版本失效、人物状态断裂、重复生成和伪造完成仍属系统问题。

用户已选择的工作方式：

- 一台机器，同一时刻一个活跃项目。多个故事顺序测试；项目内可以并发准备、独立镜头、审核与必要的决策任务。
- Producer 的组合预设作为实验默认：按需专业预铺、Producer 主执行、困难升级、独立机器审核与有界修复。是否成为长期最佳结构尚待研究。
- 获授权的例行制作与修复自动推进，完成后给用户看片；机器审核通过和用户最终接受分开记录。
- 测试剧情服务于系统负荷：悬疑交流、要塞突入、空间站事故等，可写实或动画，不做无聊乡村寻物剧情。
- 今日视频配额接近耗尽。**本次任务只准备研究，不发起媒体生成、不切换收费后备模型。** 以后实验仍按实际账户与模型限制排期。

目标是在这些约束下寻找适合的结构，不能先验断言“Agent 越多越快”或“所有专家都应取消”。

## 2. 必须区分的五个层次

| 层次 | 当前含义 | 不能混淆为 |
| --- | --- | --- |
| 产品角色 | Producer、编剧、角色/资源、场景、导演、装配等职责 | 每个角色必有一个常驻独立进程 |
| Skill | 可按需加载的方法论与操作知识 | 加载 Skill 就新增一个并行 Agent |
| Agent 会话 | 有上下文、工具和授权的模型执行循环 | 原生系统线程或供应商视频任务 |
| 程序执行器 | 校验、队列、依赖、收货、版本、装配等代码 | 每一步都必须问模型 |
| 外部模型任务 | 文本/视觉请求与图片/视频供应商在途任务 | 本地 worker 数或成功文件数 |

研究应分别绘出决策、执行、数据写入和恢复关系。角色可以保留为产品入口或专业能力，而不必固定排成长串模型回合。

## 3. 已有基础：以报告为依据，当前代码仍需核验

### 3.1 角色、模式与工具

Phase55 源码核验报告列出 Producer + 9 个 Specialist：其中编剧、角色/资源、场景、导演、装配五个是原生 tool-loop，另有 production_planner、shot_producer、continuity_reviewer、editor 的 capability 路径。“六员链”指 Producer 加前五者；不是注册表总共只有六个 Agent。

只有 Producer 具有委派能力的说法来自当时注册表。已有 scoped grant、TTL、撤销和审计，允许 Producer 在授权范围直接使用专家工具；Skill 采用目录常驻、按需加载。扩大工具权限与增加独立会话是两种不同改动。

报告记录五类协作预设：六员链、Producer 主执行、专业预铺后主执行、主执行遇难升级、组合模式；共享 runtime、工具与会话机制。W09 是六员工作流模板。已有 run 快照和模式入口，**这不等于所有可能的协作结构都已实现或充分测试**。

### 3.2 事实、输入和版本

canonical 是项目事实依据；协作 run、交接包、日志、未来的决策池都不应变成另一份可独立修改的项目正册。已有 generation_basis/input_manifest、版本选择、审核回执、fresh/stale 和修复范围等机制。

Phase54 暴露过路径不等价：部分 Producer 视频走 UNBOUND，未实际消费 Look/场景参考，而六员路径走 BOUND。Phase55 报告称统一了视频契约、提交前校验和输入清单。因此早期成片或速度差异包含输入链差异，不能全部归因于角色数量。

场景绑定与镜头接续也不是同一件事。须区分：前镜已选视频的真实尾帧硬依赖、尾帧仅作参考、新融合首帧、原生多参考、已规划的独立镜头与正常电影切镜。**同地点不自动等于必须尾帧串行；故事组也没有固定镜数。** 实际参考方式和有效性仍应由请求证据确认。

### 3.3 并发与写入

Phase55 报告记录 JobQueue、视频在途档位、轻任务并发、配额与限流桶，并指出档位配置不等于已完成真实收益验证。

重要边界：当时 `ProjectStore.update_shot` 是整文件原子写，**没有普遍的 CAS/owner 检查**；部分保护来自项目内 asyncio.Lock、ChangeSession 和工作流回执。不能写成“已有完整并发事务保障”。当前 Phase56 是否补齐，需看代码。

### 3.4 恢复、上下文与审核

Phase55 报告记录：Provider task ID 持久化、同一 video_id 收货去重、上下文用量记录、交接包、新会话 relay、项目主控租约和 generation fencing、独立视觉抽帧审核。

但仍有当时的缺口：提交已被远端接受而本地未获得 ID 时无法可靠对账；同 video_id 去重不阻止两个不同 ID 的逻辑重复提交；watchdog 延长观察不等于解决所有恢复路径；租约文件损坏曾 fail-open；自动接力次数耗尽不能伪装完成。当前状态必须重新核验。

当时的独立审核是在 Producer 完成后尾批运行，并非完整生成/审核流水。fresh 无状态视觉调用可隔离制作上下文，但同模型不等于完全独立盲审；视觉调用仍耗模型时间、额度和并发容量。

这些现象使“把机械推进从 Producer 回合中拿走”成为有价值的研究方向。它们尚不能单独证明“注意力串行是唯一瓶颈”“视频时长无从优化”“专家应全部退出执行”。

## 6. v3 提案及必须挑战的边界

提案结构：一个主 Producer；按需孵化单镜子 Producer；子任务写过渡决策池；lane-A 自动合并机械安全改动，lane-B 等主笔判断；确定性流水线自动校验、提交、依赖派发、收货、审核与有界修复；专家主要作为 Skill、会诊和独立审核。

这是一种候选方案。研究应特别检查：

1. **子 Producer 是否有净收益。** 若大部分延误来自确定性调度缺失，单 Producer 加程序执行器可能足够；不能先建池和子群再寻找用途。
2. **子任务的身份与授权。** 子 Producer 是否误入现有项目主控租约，和主笔争同一个主控资格？从单镜扩到上游会影响哪些下游版本、在途任务和审核？
3. **单镜不代表独立。** 不相交的字段或镜头也可能共享资产、场景、角色状态与依赖版本。lane-A 的前提应包括读集、写集、版本与失效影响，而不只是“带 PASS 回执”。
4. **append-only 的含义。** 已落盘条目的 status 若原地修改，就不再是纯追加事件；应研究追加状态事件与派生视图，或轻量事务存储。多写者追加、截断、重复与重放也需处理。
5. **谁是实际提交者。** 主笔与程序自动合并都能改正册时，“唯一写者”应落实到统一授权提交路径，而不是一句口号；不要另建第二套真相。
6. **名字归一。** 优先角色ID、显式别名和精确映射；唯一模糊命中仍可能错认角色，不能为了减少拒绝而静默改错台词归属。
7. **审核与修复。** 自动抽帧是程序工作，视觉判断是模型工作。同输入重复抽签与改变打法的修复应分开；不预设所有错误都重掷3次。
8. **收益估算。** 容量3、5镜并不自动得到8–9分钟。真实依赖、长尾、审核选版门槛、RPM、视觉并发与汇总都可能改变上限。

## 7. 研究应比较的路线

至少比较以下候选；允许合并或提出更好的路线，但需先说明现有能力可复用多少。

- 改良六员：保留专业决策，缩短无必要的串行交接，由公共程序执行器推进。
- 单 Producer + 按需 Skill + 确定性依赖调度 + 独立审核。
- 主 Producer + 有界专业 Worker；Worker 返回候选与证据，由统一路径应用。
- 专业任务图驱动：保留职责与独立上下文，由事件调度，而非全能子 Producer。
- v3 决策池 + 动态子 Producer；论证其额外复杂度何时值得。

重点比较延迟、人工介入、文本/视觉成本、配额浪费、状态冲突、错误恢复、可观察性、迁移成本和用户可理解性。不要只比 Agent 数量。

## 8. 定量研究的最低要求

分别统计全流程时间、固定输入后的生产时间、远端生成时间、决策排队、模型请求时间、可派发后延迟、审核等待和收尾。并行区间不能简单相加当作墙钟。

对固定视频任务和恒定容量 C，可用 `max(最长依赖路径耗时之和, 全部任务耗时之和/C)` 作理想调度下界；它不是实际可达承诺。若依赖必须等审核或选版，相关工作也必须进图。

本交接做了一次纯合成校验：5个等时200s任务、仅1→2依赖、容量1/2/3、无审核及外部限制，用工作就绪即派发的示例调度分别为1000/600/400s。容量3时若下游就绪后额外等待650s，示例变为1050s。它只说明决策等待可能吞掉并发收益，**没有复现 Phase56，也不能推出真实样本可以节省650s**。研究者应使用取证包时间线重放并做敏感性分析。

实验要先冻结负荷、输入策略、版本、模型和修复规则。先做“只有程序自动推进”的消融，再测试“额外模型决策并发”的增量；避免把二者一起改后全部归功于多 Agent。少量样本只作为探索性证据。

## 9. 公开研究起点与使用限度

2026-10-18 核对了以下官方材料，供研究者重新检索、扩展和核验版本：

- [Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)：按任务选择可组合的工作流、并行或动态委派，复杂度须由收益证明。
- [Anthropic：Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)：展示可分解研究任务的并行收益，也说明上下文依赖与调用成本的限制；不能把其研究场景收益直接套到视频制作。
- [LangGraph：Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)：区分线程检查点与跨线程存储；仅有内存记录不足以支持进程重启恢复。
- [LangGraph 官方 Functional API 源文档](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/functional-api.mdx)：恢复与副作用边界、任务重放和幂等需按实际版本核对。

这是机制参考，不是框架采购建议，也不是本系统能力证明。原来的 durable-execution 文档地址本次访问跳转到了 persistence，应引用实际落地页面或对应源码，避免沿用过期标题。
