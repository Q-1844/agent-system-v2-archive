## 0. 一页摘要

实测证明：并发灶台（视频 1/2/3 路）机制真实生效，但单片墙钟无改善——瓶颈不在容量，在**大模型串行注意力被流程性杂务占用**。据此提出目标架构：**大模型只留决策点，其余全部程序化；决策点之间用"子 producer + 过渡记录池"实现并行**；专家体系从流水线节点降级为方法论库/会诊对象/独立审核员。本文给出证据、架构、合并规则草案与 10 个待决问题。

## 1. 证据基础（全部来自 Phase56 B/C 正式实测）

### 1.1 时间账拆解（P1 五镜片，容量 3 档，总 1159s 花在哪）

| 阶段 | 耗时 | 性质 |
| --- | --- | --- |
| LLM 准备（授权完→首次提交） | ~30s | 大模型（必要） |
| 提交前闸门拒绝→LLM 重试波次 | 13 次/三场，每次 ~50-90s | **流程性杂务**（台词名 vs 角色名册不一致、basis 时序）——0 额度但吃 LLM 回合 |
| 视频净生成 | 中位 176-243s/条，最长 357s | 供应商物理时间（±50% 方差，快不了） |
| 依赖镜提交延迟 | c02 晚提交 **650s**（上游 224s 就绪，LLM 忙于重试波次） | **单点最大浪费** |
| 末收货→装配/汇报 | ~190s | 大模型+程序混合 |
| 独立终审（视觉抽帧） | 180-292s | 视觉调用（可并行，与大模型无关） |

### 1.2 关键定性结论〔实测〕

- **不是视频过不了审**：video_review_v2 政策下三场两场零硬错零修复；终审不是瓶颈。
- **不是首帧过审**：首帧包内冻结，运行期零重生成。
- **并发机制真实生效**：峰值在途 1/2/3 各自达成；热重配（run_reconfigure）落档实证。
- **串行大模型注意力=瓶颈**：单 producer 的回合间隙（17-90s/次）与决策延迟（650s）吃掉全部并发收益。
- **程序自动修复有效但有限**：INF2 的 c02（multi 三参考接力镜）3 次确定性重掷全败（身份硬错）——**需要换打法时程序无能为力**，这正是大模型决策点的实证位置。

### 1.3 视频模型能力画像〔实测〕（协作模式适配的依据）

| 能力 | 实测 | 协作含义 |
| --- | --- | --- |
| 单条时长 | 3-6 分钟，±50% 方差 | 灶台满转是唯一对抗方式；空闲=纯浪费 |
| 并发容量 | 3 outstanding 实证 | 独立镜头≥3 的负荷才有意义 |
| 首帧锚定 i2v | 身份最稳 | 能走首帧锚定就走首帧（机器人案例：首帧 prompt 做到了 Look 管线做不到的） |
| multi 三参考接力镜 | 身份最脆（3 修全败案例） | 接力链是全链最脆环节，重点盯防 |
| 提交前预检 | 本地秒级、零额度 | 所有校验前置到提交前，失败不留到队列里 |

## 2. 目标架构〔提案〕

```
┌────────────────────────────────────────────────────────┐
│ 主笔 producer（每个项目一个，持有项目级主控租约）          │
│   开工：一次完整规划（故事/分镜/接续策略/负荷分解）        │
│   平时：只扫决策池中「需判断」条目 + 处理升级              │
│   末尾：装配决策（选版清单确认）                          │
└──────────────┬─────────────────────────────────────────┘
               │ 交接包（窄化：单镜授权+错误历史+池写入方法）
       ┌───────▼────────┐
       │ 子 producer 群  │  决策点出现即孵化，完毕即回收
       │ （单镜级授权）   │  能修→写决策池；卡了→升级专家/留主笔
       └───────┬────────┘
               │ 写入（不碰正册）
       ┌───────▼─────────────────────────────────┐
       │ 过渡决策池（append-only JSONL）           │
       │  lane-A 机械安全类：带完整回执→程序自动合并 │
       │  lane-B 判断类：排队等主笔扫               │
       └───────┬─────────────────────────────────┘
               │ 合并/应用
       ┌───────▼─────────────────────────────────┐
       │ 确定性流水线（零 LLM）                    │
       │ 名字归一→批量提交→依赖秒级派发→收货入库    │
       │ →攒批终审（视觉并行）→有界自动修复→装配    │
       └─────────────────────────────────────────┘
       专家体系（降级后）：方法论库(Skill)/会诊升级对象/独立审核员
```

三条设计公理（与既有约束相容）：
1. **正册唯一写者**不变：主笔（或 lane-A 程序合并）之外无人写 canonical——子 producer 只写池。
2. **大模型只出现在决策点**：排队/提交/收货/派发/归一/终审全部程序化或视觉调用。
3. **一切留痕**：池=append-only，合并/驳回全程审计（沿用回执体系）。

## 3. 关键机制草案

### 3.1 过渡决策池〔提案〕

- 载体：`output/agents/decision_pool/{run_id}.jsonl`，append-only；条目={decision_id, scope(shot/asset), type, payload, receipts, status: pending/applied/dismissed, actor}。
- **lane-A（自动合并）准入标准〔待决 Q2〕**：改动域不相交（单镜）、机械可验证（带 passing 校验回执）、不触发聚合状态（选版/装配/跨镜关系）。满足→程序合并进正册+池内标记 applied。
- **lane-B（等主笔）**：跨镜关系变更、策略改变（如"c02 改打法：重做首帧"）、聚合状态。主笔在下一个决策点间隙批量扫。
- 子 producer 卡住时的两条出路：升级专家（见 3.3）或写 lane-B 条目后自我回收。

### 3.2 子 producer 生命周期〔提案〕

- 孵化触发：终审硬错（确定性修复耗尽后）／主笔决策积压超阈值〔待决 Q3〕。
- 上下文=窄化交接包（现有 handoff 包机制缩到单镜）：该镜错误历史+修复授权+池写入方法+相关 Skill 引用。成本≈主笔的零头。
- 授权=镜头级（只能改本镜及其真实依赖链上游的输入）；不能动聚合状态。
- 回收：决策写入池即结束；不驻留。

### 3.3 专家体系降级〔提案〕

| 原角色 | 新角色 | 保留理由 |
| --- | --- | --- |
| 流水线节点（六员链） | **废止**（W09 模板保留为显式质量基线对照） | 实测慢 2.7 倍+模板无法消费冻结包（P56_C 报告 §2） |
| CD/SD/Director 的 Skill 方法论 | **方法论库**（producer/子 producer 开工 load） | 三查判据/时长配方/场景锚方法有效 |
| 疑难处理 | **会诊升级对象**（内容策略措辞等 P54-B3 实证场景） | 保留 |
| 审核者 | **独立审核员**（fresh 视觉调用）——**唯一必须独立于 producer 上下文的角色** | 学生不能给自己判卷 |

### 3.4 确定性流水线补件清单〔提案〕（P3 演练前落地）

1. **名字归一**：提交前预检的说话者名与角色名册做包含/模糊匹配，唯一命中→本地自动改写+留痕（消灭 13 次/3 场的那类拒绝）〔待决 Q6：归一规则边界〕。
2. **依赖自动派发**：收货事件→查依赖图→秒级自动提交下游（消灭 650s 延迟）。
3. **攒批终审**：终审从"每 run 一次尾批"改为可配置批次粒度〔待决 Q7〕。

## 4. 与 GPT 探讨的十个待决问题

| # | 问题 | 背景/选项 |
| --- | --- | --- |
| Q1 | 决策池 lane-A/B 的分界线怎么画？ | 候选标准：改动域是否单镜+是否可程序验证+是否触及聚合状态。边界案例：改接续策略（单镜但影响下游依赖图） |
| Q2 | lane-A 自动合并的置信条件？ | 选项：回执齐全即合并 / 回执+抽检复核 / 一律等主笔（最保守） |
| Q3 | 子 producer 孵化触发条件？ | 选项：仅确定性修复耗尽后 / 决策积压≥N / 主笔回合超时。过早孵化=成本，过晚=灶台空转 |
| Q4 | 子 producer 与主笔的授权边界？ | 镜头级够不够？"真实依赖链上游"（如重做 c02 需要动 c01 首帧）算谁的权限 |
| Q5 | 主笔多久扫一次池？ | 事件驱动（池有 lane-B 即通知）vs 决策点间隙 vs 定时。事件驱动最紧但可能打断主笔当前决策 |
| Q6 | 名字归一的规则边界？ | 包含匹配唯一命中即改？多候选/零命中怎么办（拦 or 问）？要不要把"归一"也做成池条目留痕 |
| Q7 | 终审批次粒度？ | 全批（最省 LLM 间隙，但硬错发现晚）/ 分波（每 2-3 镜）/ 收货即审（并行度最高，回到旧模式） |
| Q8 | 修复的升级梯度怎么定？ | 程序重掷×3 → 子 producer 换打法 → 专家会诊 → 主笔。每级的进入条件和最大次数 |
| Q9 | 专家体系的最终形态？ | 全降级为库+会诊 vs 保留某个 specialist 的独立 turn 能力 vs 只留审核独立原则。六员模板的维护成本要不要继续付 |
| Q10 | 理论上限核验 | 若全部落地，P1 类五镜片视频阶段理论 ~8-9 分钟（当前 1159s）——这个估算对吗？瓶颈会转移到哪里（供应商方差？终审视觉额度？） |

## 5. 与既有约束的关系（不违背）

- 00-06 任务书约束：正册唯一、主控纪律、授权留痕、用户最终看片、失败不冒充成功——全部保留；本提案是**执行层**改造，不动事实底座与授权模型。
- 与 06 校验文件的关系：Q10 的理论上限需要像 06 一样先做合成边界校验（DAG 枚举×容量×决策延迟模型）再真机。
- 与 D 批的关系：确定性流水线补件（3.4）正是 D2"确定性推进"的范围；P3 恢复演练=第一次真机检验。建议 P3 演练时同时埋点：主笔每决策点耗时/决策扎堆度/池子条目分布——为 Q3/Q5/Q10 攒数据。

## 6. 验证路径（建议）

1. **P3 前落地 3.4 三补件**（小件，定向测试即可）→ P3 演练按新流水线跑，埋点攒决策数据。
2. 用 P3 数据回答 Q3/Q5/Q10 → 定稿池与子 producer 设计。
3. 子 producer+池作为新版本批次实施（与 P3 的 awaiting_relay/resume、热重配同栈）。
4. 对照验收：同负荷下"主笔决策耗时占比"与"灶台占用率"应显著改善；画面质量指标（v2 终审硬错率）不回退。
