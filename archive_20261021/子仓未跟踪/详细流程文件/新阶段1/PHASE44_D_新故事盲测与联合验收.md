# Phase 44D｜视频 Skill 独立盲测、故障演练与成片联合验收

本文件供 zcode 在 Phase 44A 完成冻结后执行。可与 B/C 的实现并行；D 的**盲测成绩只统计冻结版本的新会话**，不合并之前《雨灯归航》的修复数据。

## 可直接执行的任务书

你负责证明现有视频 Skill 在一个新故事里能由系统 Agent 自行使用，并最终检验“生产镜头 → 选片 → 成片 Agent → 用户观看”的闭环。`PHASE43_REPAIR_SKILL_BLINDTEST_REPORT.md` 明确说 Phase 43 的盲测夹具已准备、**正式新会话尚未启动**。先核验报告，再执行，不要把文件名中的“BLINDTEST”当作已盲测通过。

### D0. 冻结与受测材料分离

记录代码/Skill/注册与加载配置/视频模型/已批准 Look、道具、场景视图的 commit、版本和可复核哈希；报告中的《晨露快递》夹具及批准情况要逐项核对。测试控制方可以知道历史问题和预期检查点，但受测系统 Agent 的任务书只能给故事目标、角色与道具要求、可用已批准资产及产出要求。**不透露**旧项目镜头 ID、`crop` 的适用答案、三参考哨兵何时启用、分拍粒度结论、按镜修法矩阵或可接受候选位置；正式 Skill 自身可正常加载。不要在受测项目里塞先验“正确镜头方法”。

把评审用的夹具和任务原文归档，保留受测会话 ID 与入口回执。按报告 §3.3 指示审计实际 API/脚本后，通过用户平时使用的正式 Producer 入口新建会话；进程内测试脚本可以做核验，却不能替代正式入口的盲测。

### D1. 新故事完整生产

若《晨露快递》经核验仍可用，使用已获用户批准的榛果 Look×2、晨雾草原/老橡树视图与露珠信道具。让 Producer/专业 Agent 在 canonical 中建立故事段、镜头与 Binding，生成视频候选并自主选择方法。故事应自然包含角色身份维持、道具入画、同一过程内接续、一次合理切镜、场景变化；不要为了覆盖某个技术路径强行插桥。

对每镜保留：选择前可见的项目事实/Skill 加载、Agent 理由与 options、实际 Binding、编译后的 provider 模式与参考资产顺序、任务 ID、请求与回执、视频首/中/尾帧、末态、依赖、用户评语、final 指针。记录所有候选包括失败样本，不仅保留最后赢家。检查镜头总数和生产成本时按实际账本口径，不把墙钟误写成视频内容秒数。

给用户提供**逐镜及整段可播放评审页**，每镜尽量精简到少数关键候选但保留完整后台证据；评论需落每轮独立档，避免切 manifest 覆盖反馈。用户判定五维：角色身份/造型、道具样式与状态、场景空间、动作与尾态、整体叙事及剪辑观感。视频生成成功、视觉模型通过、用户愿意选入正片，三者分别记录。若用户尚未看片，写“等待人评”，不得自行宣称盲测通过。

### D2. 隔离故障演练

用与正片完全隔离的 mini 项目或测试资源各演练一次：①上一镜尾帧含错误特征；②需要的场景参考缺失或不可公网读取；③提交成功后进程/轮询中断再恢复。每项的预期是 Agent/系统**识别、给出合适动作、保留可追溯回执**，不是一定生成新视频。错误端点不得被盲目接力；缺场景应走正式资源补齐或诚实阻断；恢复应查原 task ID，避免重复提交。若某能力需要付费生成，先给最小成本计划，在已授权的测试范围内只做必要候选。

### D3. 失败归因与修正规则

将每个失败按证据归入：A 方法选择错或 Skill 未加载，B 数据/Binding/编译/工具或权限错，C 请求和方法正确但模型随机候选差，D 审美与叙事口径需人评。A 可能需要改正式 Skill；B 修系统或数据；C 可有限重采样并记录方差；D 等用户反馈。不能用“多生几组”掩盖前两种问题。

如需改代码、Skill 或批准资产，保存本轮原始失败，明确旧冻结失效，重新打版本并开**全新会话**复验；不把修复前后片段拼作同一轮盲测成功。若只是用户在同一冻结输入里挑出合理候选，保留选片时间和依据即可。系统若自动把新视频设为 final，复核并按用户裁定回拨。

### D4. 与成片线的合流

优先用 A 已冻结并获用户选片的《雨灯归航》作为 B/C 的真实后期验收样例，避免让盲测一边生产一边改变成片输入。待《晨露快递》逐镜人评和正式选片结束，再由 Assembly Agent 对**新项目**做一次小规模迁移验证：只读已批准镜头、生成自己的时间线与旁白提案、导出连续画面及一条连续音乐；用户可比较它与旧片成片是否都工作。不要把后期剪辑不佳归责给视频 Skill，也不要把镜头视觉不佳算成混音失败。

### D5. 验收门槛与报告

不预设“90% 镜头通过”这类掩盖关键失败的数字。技术硬门槛：正式入口的新会话及 Skill 加载可证、无错误资产偷换、关键任务可恢复、候选与 final 可追、媒体可播放、冻结版本无暗改。视觉门槛：所有进入**正式成片**的关键镜头均有用户逐镜接受记录；少量失败候选可以保留为证据，但不能混进成片。若某非关键镜头仍待评，报告列明而不封板。故障演练达到“安全阻断或正确恢复、可解释、不污染正片”。

提交 `PHASE44_D_REPORT.md`：冻结表、任务原文、会话/工具轨迹、新故事每镜候选和评审、故障三案、失败归因、真实内容秒数与请求次数、回归测试、是否改版及新会话复验、用户最终意见。最后**分别**给出三项判定：视频 Skill 当前模型范围是否可封板；基础成片 Agent 是否可用于日常剪辑；MiniMax 旁白+音乐是否达到本次短片的交付效果。若未通过，列出最小阻塞和下一批单一目标，不在同一报告无限扩项。

## 发给受测 Agent 的任务模板（只允许故事目标，不含解法）

> 请在本项目中根据已批准角色、道具和场景资料，制作《晨露快递》的简短动画。先核对项目事实和当前可用资源，建立清楚的故事过程和镜头顺序，完成角色送达露珠信的故事。逐镜生成可选视频，记录选择的依据、实际使用的资源和生成结果。检查人物、道具、场景、动作以及镜头之间的叙事是否一致，交付供我逐镜观看与选片的材料；遇到资料缺失或生成失败，按系统正式流程处理并如实报告。

该模板在使用前应与已批准夹具的真实故事要求核对；若夹具另有最终任务原文，优先使用冻结的原文，确保受测 Agent 从未看到控制方答案。
