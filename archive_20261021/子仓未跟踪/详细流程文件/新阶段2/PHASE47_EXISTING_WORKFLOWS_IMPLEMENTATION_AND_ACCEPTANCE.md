## 4 B 批 补齐真实生产所需的交接语义

### 4.1 先修 character_designer 正常路径

复现报告中的 OCC `reference_required`，保存失败工具名、入参、期望 revision 或指纹、真实错误和当时对象状态，确认第一处偏离。

区分至少四种情况：创建新对象时错误要求已有对象引用；已有对象更新没有先读取并携带正确 OCC 依据；资源生成确实缺少身份或源图；回执到工作流完成校验之间映射错误。

分别在职责工具或 adapter 的正确层修复。禁止关闭 OCC、给所有引用塞默认值、提前写“已批准”或伪造资源，以此消除报错。

需要完成两个真实正例：

1. 新项目从文字设定依法创建角色、Look 和参考图候选，交给人审。
2. 已有经用户批准 Look 的项目依法生成一个新视角或新造型候选，并保留原版本。

若当前架构确实需要在两个动作之间审批，把它拆成两个 character_designer 节点和一个人工审核，而非在单个 turn 内等待外部决定。节点实例数增加不等于增加新 Agent。

### 4.2 节点完成不能只看写域变化

沿用 `changed_refs` 做写入证据，但必须按本节点目标检查具体输出。

| 节点目标 | 成功必须证明 | 不能当作成功 |
| --- | --- | --- |
| Producer 计划 | 持久化计划结果，含目标、任务范围、依赖、待决定项；来源可追溯 | 只有“计划好了”的聊天回复，或私自完成下游任务 |
| 写故事 | 指定范围的故事段或正文已存在，真实版本和写入回执匹配目标 | 改了无关段落，或只返回摘要 |
| 角色资源 | 指定角色、Look、道具或参考候选齐备，生成文件可读取，审批状态诚实 | 只创建角色条目，尚无所要求的参考图 |
| 场景资料 | 指定 Location、SceneInstance、视图和需要的图像产物齐备 | 只新写地点文字，没生成要求的场景视图 |
| 分镜准备 | 镜头清单、正式资源绑定和所要求的分镜图候选齐备 | `shots` 有变化，但目标首帧未生成 |
| 视频制作 | 目标视频版本已完成、可读取和播放，provenance 与请求、任务一致 | 创建 shot，或仅提交了一个尚未完成的视频任务 |
| 视频修复 | 新候选和前后对比齐备，保留原版并说明影响范围 | 改了 prompt 或元数据，没有新修复结果 |
| 装配成片 | Sequence、镜头版本快照、所要求音轨、完成 render 和可播放文件齐备 | 只创建 Sequence，或导出任务还在运行 |

该表是本轮需落实的验收契约，不是断言所有输出已经有统一字段。先复用现有结果和资源引用；必要时增加少量有类型的结果要求。不要做一个全业务 schema 重构。

候选交付节点可以在候选齐备后成功，再进入人工审核。不要反过来要求该节点先拿到用户批准才成功，造成前后互相等待。

### 4.3 增加显式且可验证的复用

建议在 Agent 节点配置中增加两种完成策略，最终命名按真实契约调整：

- `require_new`：默认策略。目标要求本 attempt 产生所指定的新产物或有效更新。
- `allow_verified_reuse`：仅当节点明确允许复用时启用；Agent 读取并核验目标对象，服务端对引用和条件独立检查，可以返回真实复用结果。

`allow_verified_reuse` 不是无写入就放行。必须检查项目归属、对象存在、具体版本或内容 hash、文件可读、目标要求、必要审批、freshness 和依赖兼容。留存读取或核验回执及采用理由。

复用输出记录 `reusedRefs` 或既有等价字段；新增输出记录 `changedRefs`，两者不混写。候选复用与已选素材复用也要分别标明。

需要四个定向情景：合格故事正常复用；新写目标不能以旧故事冒充；过期视频不得复用；混合任务只补缺图、如实复用已合格图。

旧定义没有新字段时保持原 `require_new` 语义，不静默降低验收要求。真正的只读分析任务可以返回可验证的计划或分析产物，但不能把“读了一遍”冒充新的图像、视频或成片。

### 4.4 交接以具体范围和版本为单位

交接包至少能表达：run、节点、attempt、AgentTask 关联；目标故事段或镜头集合；具体产物 ID、版本或 hash；创建或复用；审批与选片状态；摘要、警告和缺项。

```json
    "attemptId": "示例尝试"

  "scope": {"shotIds": ["示例镜头一", "示例镜头二"]},

    }

```

禁止“去项目里找最新的视频”作为正式交接。不得从整个项目的变化中认领其他 turn 写入的资源；节点目标、工具回执、workflow correlation 与产物 provenance 应交叉一致。

后续节点可以读取项目 canonical 取得必要全局上下文，但采用的产物必须在本节点范围或明确声明的补充依赖内。补充依赖要留引用，不能暗中切成历史版本或最新版本。

producer 的计划可填充模板已声明的任务范围和目标参数，不能在运行中插入隐藏节点、改变冻结顺序或绕过审核。先按已保存的用户目标运行；计划与画布冲突时报告冲突，不私自重排。

### 4.5 正确处理逐节点输入冻结

run 固定定义、配置、Agent 基线、Skill 内容与模型政策。每个节点在正式派发前解析上游输出，再固定其具体输入版本与指纹；上游尚未生产的素材不能在 run 启动时假装已固定。

保留 run 启动的 canonical 指纹作审计，同时用范围明确的逐节点依据检查外部变更。前一节点的合法写入应成为下一节点的新依据，不能被误判为“项目从启动时变了”而拒绝整链。

同一类 Agent 的两个节点必须具有不同 nodeId、attemptId 和关联记录；上下文不能将前一节点的成功摘要当作后一节点已完成。会话复用若是既有能力，仍须明确任务边界、目标和 Skill 绑定范围。

### 4.6 审核通过和正式选用必须分清

至少区分两种人工审核用途，仍属于一种人工审核组件：

1. 检查或创作确认：用户对冻结对象表示允许继续，不必更改 selected 或 final 指针。
2. 批准或选用产物：下游需要被批准 Look、首帧或正式选用的视频，必须由用户通过现有用户专用入口完成具体选择。

审核通过不能自动替用户选一个候选。审查者姓名文本不等于认证身份，不因填写“制作人”就取得该用户权限。

首选在审核卡片中复用现有批准或选片 UI 与真实调用；可提供“通过并选用”这样的明确动作，前提是用户看见具体候选和后果，该操作由用户身份触发既有入口。模型和工作流执行器不获得用户选择权限。

若直接复用不合适，提供跳转到现有资源、分镜或视频选择页面的入口，返回后由服务端核验用户已选择的精确版本。必要选择未完成时，节点保持 `waiting_human`，展示具体缺项。

对于两个先后执行的用户操作，不能假定“选片请求”和“审核决策”跨服务天然原子：记录待完成动作，处理结果不明并对账；两项均确认满足条件后才唯一启动下游。重复点击不能重复派发。

审核快照要区分候选文件的身份与内容、所依据的业务状态、以及用户选用动作造成的指针变更。受本审核明确授权的选用变化可以成为后续依据；无关内容或依赖变更仍需拒绝旧决策并重审。不得为解决指纹冲突而整体关闭审核对象检查。

连续两次审核各有独立 reviewId、对象、意见与决定。第一审通过不替第二审决定；二审意见不能覆盖一审意见。界面必须各自真实等待。

本轮驳回仍停止下游。用户修改目标后发起新运行，或使用已有正式重试机制处理可恢复失败，不把它画成已经实现的自动返工循环。

### 4.7 assembly 必须接收真实可用素材

先用隔离项目里少量真实、用户已选的视频验证 assembly 工作流入口，再接六员整链的本轮新视频。

成功应证明实际采用的是交接包里指定的镜头版本，Sequence 顺序与用户目标一致，旁白和音乐输入有版本记录，最终 render 可播放。不能只有 `sequences` 写入便标记成片成功。

保留现有男声偏好和已有音频配置；具体 voice_id、TTS 模型和音乐来源仍从当前项目配置核实，不从旧报告猜 ID。不因官方已有新 TTS 型号而顺手升级。MiniMax 需校验业务状态、真实音频内容并持久化；URL 返回有有效期，不能只保存临时地址。[S5]

本轮主成片采用“原视频静默或明确控音、外部旁白、连续音乐或明确的分场景音乐”的已讨论方向。是否保留原生环境音需明确记录，不能将原生对白与旁白叠在一起后不检查。

## 5 C 批 落地十类现有能力工作流

### 5.1 模板怎样落地

优先用项目现有定义格式实现参数化模板。模板是一份可复制的工作流定义及默认目标，不新增独立运行引擎。

正式页面应至少提供“从模板新建”和现有保存、校验、运行能力。复制模板产生新工作流身份，保留模板版本来源；用户可以改目标、节点顺序、Skill 绑定和审核次数，随后由服务端校验合法性。

每个模板交付真实定义、可运行配置样例、所需输入说明、预期产物和一条真实运行证据。只把名字展示在下拉框、只导出 JSON、只运行测试脚本，都不能算该模板已落地。

模板中的 Skill ID 必须来自真实目录；可绑定对象以名册为准。assembly 不得因模板需要而绕过现有绑定限制。

### 5.2 模板清单

下面的箭头表示执行先后，Skill 另作绑定；“审核”只在相应产物准备后等待。

| ID | 名称和执行链 | 必需输入 | 本轮需交出的真实产物 |
| --- | --- | --- | --- |
| W00 | Producer 生产计划 → 审核 | 故事目标、已有项目状态、任务范围 | 持久化计划与待决定项；无隐藏专业委派 |
| W01 | 编剧写作 → 审核；可在前方插 Producer | 创作简报、新写或修订范围 | 实际故事段或正文版本及回执 |
| W02 | 角色资源 → 审核；按前置条件可重复角色节点 | 角色、Look、道具目标或已有批准资源 | 新参考图候选、明确版本、合法复用记录 |
| W03 | 场景设计 → 审核 | 故事段、地点、时段及空间目标 | Location 与 SceneInstance、实际环境视图 |
| W04 | 导演分镜准备 → 审核 | 故事、资源、场景的具体引用 | 镜头清单、资源绑定、真实分镜图候选 |
| W05 | 导演视频制作 → 审核 | 经批准首帧或合法参考素材、镜头范围 | 真视频版本、生成依据、首中尾帧与候选清单 |
| W06 | 导演诊断与修复 → 审核 | 已知问题的视频或根帧、反馈与范围 | 修复候选、前后对比、影响下游清单 |
| W07 | 导演有效端点桥接 → 审核 | 两个合格且拟保留的端点和真实接缝问题 | 桥接候选、双端请求依据与拼接预览 |
| W08 | 装配 → 审核 | 已选视频版本、旁白和音乐政策 | Sequence、真实 TTS、音轨、完成 render |
| W09 | 六员完整生产及独立双审核 | 新故事目标、本轮合法资产审批 | 从新故事到可审成片的完整证据链 |

这些流程中的同类节点可以被用户重复插入。例如“场景设计 → 一审 → 二审 → 导演”属于现有顺序能力；“导演分镜 → 人审 → 导演视频”也是现有能力组合。它们不要求新增组件。

### 5.3 W00 和 W01

W00 验证 producer 可以只做目标拆解与协调计划；保留 WF_DELEGATE_GUARD，不能在该节点内私自调用其他五员。计划中建议某个 Agent，不等于已经派发该 Agent。

W01 至少真实运行一次新写故事，再用另一运行验证修订和合法复用。审核对象指向具体故事版本。下游读取实际故事，不从 producer 的自然语言总结重建另一份故事真相。

### 5.4 W02 和 W03

W02 必须实际产出角色或 Look 图像，不能沿用 Phase 46 的阻塞结论作为正例。W03 必须实际产出有用途的场景图像，不能只证明地点文本写入。

两者至少各有一次“创建候选—用户审核—下游正式读取”的完整记录。涉及批准的地方复用现有用户机制；需要补缺资产时只补缺项。

### 5.5 W04 和 W05

W04 负责形成镜头和分镜图候选，审核使必要首帧或素材可供视频制作。W05 负责真实视频生产，把视频完成与用户选片分开。

W05 中至少一个 director 节点绑定正式尾帧接力校准 Skill。让系统 Agent 根据故事与资产决定接续、重建或正常切镜，测试者不要逐镜指定答案。

影像检查至少覆盖开头、过程、最后一秒和提取尾帧；核验身份、造型、道具、空间、动作、剧情尾态。API 返回成功不等于画面合格。

### 5.6 W06 诊断与修复

本流程不新增“Repair Agent”，也不假设注册表已有第三个修复 Skill。先检查现有正式 Skill 是否包含已沉淀的诊断和修复规则，依名册绑定已有适用 Skill。

在隔离项目中使用有真实已知问题的候选或经授权的测试 fixture；如引用历史素材，保留来源和实际版本，不改原项目。

系统 Agent 应先判断第一处偏离位于输入资产、根帧、资源绑定、视频过程、叙事尾态还是剪辑接缝。优先保留合格部分；小偏离做当前工具支持的局部处理或小范围重生成，大偏离重建错误根帧并核验真实下游。

“局部处理”是否能编辑视频、裁剪或只重做某镜，以当前工具为准。不能因为 Grok 存在视频编辑，就给 Agnes 流程填一个不存在的编辑调用。

新修复候选尚未被用户选用前，原正式下游继续引用原选版。候选生成不自动令原版选片链失效；正式切换后再按实际依赖标记需要复核的下游，不机械全部重做。

### 5.7 W07 有效端点桥接

绑定正式 keyframes 接续桥 Skill，前提是 binding 目录确实允许 director 使用它。

必须有两个本身合格、希望保留的端点，以及实际妨碍叙事的接缝问题。可在独立测试片段中构造需要过渡的合法场景，不强迫正片为了覆盖 Skill 插桥。

正常电影切镜应判为不需要桥接；无效端点应先修端点。两个负例必须测到，但它们不能替代至少一条合法端点桥接的真实生成正例。

桥接生成后检查首中尾帧、身份、动作方向和两端拼接预览。是否加入 Sequence 仍需用户决定；不要自动改原项目已选镜头。

### 5.8 W08 现有视频装配

对已有用户选用的视频，显式允许读取或复用，而不要求 assembly 重新制造视频。assembly 仍要真实形成新的 Sequence 或新的 render 候选。

至少验证无声拼接、外部旁白加连续音乐两个目标；已有可复用音频可明确复用，整链新项目仍需有本轮新 TTS 证据。

旁白文本、voice_id、模型、实际音频时长和片段排布必须在账本中；旁白过长时由 Agent 调整文本或排布并交付结果，不无提示地截断。音乐来自当前获准素材或当前已接通生成服务，不引入新服务。

规格不同的视频应先探测并按现有装配服务归一化。FFmpeg 的 concat demuxer 对流规格有一致性要求；采用 concat filter 时需正确处理片段时间戳。[S6][S7]

### 5.9 W09 六员完整生产

建议默认链如下，节点实例可按实际批准前置条件细分：

1. producer 提交持久化生产计划。
2. script_writer 新写故事 → 故事审核。
3. character_designer 生产角色、Look 与必要道具 → 资源审核及必要批准。
4. scene_designer 生产场景与视图 → 场景审核及必要批准。
5. director 生成镜头和分镜图 → 首帧或分镜审核。
6. director 生成真实视频候选，绑定适用的尾帧接力校准 Skill。
7. 第一轮视频人工审核，检查叙事、身份、动作、空间和候选技术状态。
8. 第二轮独立视频审核，完成用户拟用于装配的具体版本选择；第一轮意见保留。
9. assembly 接收精确选片范围，制作旁白、音乐与成片候选。
10. 成片审核，交付可观看材料与用户定版入口。

这是一条顺序链，包含六种 Agent、可重复的 director 实例和多个审核。导演两次出现是为了让首帧审批发生在视频任务之前。

资源生产如需先确认基础身份，再生成造型，可重复 character_designer 节点。同样保持单链，不建立隐式返工和并行。

六员链不需要无条件绑定桥接 Skill。桥接的实测正例在 W07 完成；W09 只有真实接缝需要时才使用，保持制作判断的真实性。

## 6 D 批 新项目真实生产与用户评审

### 6.1 作品简报

新建隔离项目，暂名《风后邮站》。制作约 30 至 60 秒、二维动画风格的动作叙事短片，以外部男声旁白补充叙事，不依赖原生人物对白。

主角是一只年轻红狐，穿深青色短外套，戴米白围巾，耳尖黑色；关键道具为带圆形黄铜扣的红色邮袋。角色图与道具图须在本项目真实生成并按系统规则审批，不能把文字简报当作已经存在的批准资源。

三个故事过程：

- 清晨风后的街角：主角捡起邮袋，确认一封信没有被雨打湿，并向邮站走去。
- 邮站内：主角核对信件，将它放入邮袋，再提袋走到门口。
- 门外小桥：主角走过小桥，把信交给等候的朋友，最后回望亮起的邮站灯。

结局事实固定为信件完成交付。候选偶然出现其他行为不能静默改写结局。镜头数由系统 Agent 规划；测试夹具建议至少六镜，包含同地点连续动作、一次合理换场和一次中近景身份检查。这是验收样本要求，不写入通用 Skill 的固定镜头数规则。

可用等复杂度的另一个新故事替代，但需记录缘由；不能使用旧项目已经制作好的视频冒充全新生产。

### 6.2 执行者与受测 Agent 分工

Zcode 负责模板、API 和 UI 接线、测试记录及故障定位。系统 Agent 根据目标、canonical、正式 Skill 与工具自主完成工作。

对系统 Agent 给出作品目标、质量要求、范围和交付目标，不提供逐镜正确方法、旧项目决策答案或一份由测试者手写的实际 provider prompt。

在每个视频任务前保存简洁的事前决策：镜头位置、所用批准资源、起点与预期尾态、选择方法、当前 adapter 能力和上游版本。之后记录真实请求与结果，不能根据成片倒填事前理由。

### 6.3 必须出现的真实媒体

- 新角色或 Look 图像、道具图像和场景视图。
- 正式分镜图和资源绑定。
- 足以组成完整短片的本轮真视频候选。
- 本轮 MiniMax 旁白及持久化音频。
- 实际可用的音乐音轨与混音输出。
- Sequence 和可播放成片候选。

仅有图表、任务 ID 或 metadata 不满足媒体交付。已经提交而尚未完成的长任务，要等待真实终态或如实报失败，不先记完成。

### 6.4 评审材料

每一人工关口提供本次具体产物、版本、必要前后对照和问题。视频审核提供逐镜播放、首中尾帧、相邻接缝短预览及推荐候选。

首轮人审与第二轮人审要真实分别完成。测试者可以在隔离工程用例中提交审核决定验证机制，但不能代替用户作正式审美和选片决定，也不能把工程用例的自动同意记成用户看片通过。

成片审核至少让用户能听见旁白与音乐，查看完整播放和片段顺序。保留三种独立记录：用户觉得画面可接受；用户正式选了哪些版本；用户是否接受剧情变化。

最终 render 候选可以已完成，但用户没有 final 时，交付明确写“可审成片已生成，用户定版待处理”。如本轮完成标准要求用户定版，则保持该验收项待评，不替用户调用 final。

### 6.5 非模型质量问题不能转嫁给用户

以下问题由 Zcode 自动定位并修复：正常输入仍 OCC 拒绝、参考绑定丢失、错误回执投影、审核通过后仍缺交接、重复节点串会话、装配拿错版本、thinking 参数丢失、任务丢失和前端与持久状态不一致。

一次模型候选不好，允许系统 Agent依法生成新的候选。只有真实定位到 Skill 决策缺陷，才修订 Skill；不能看到结果差便盲目加一堆全局规则。

## 7 E 批 真机恢复与故障处理

### 7.1 保留现有恢复模型

不为了本轮引入完整 `waiting_external` 状态改造或异步图执行系统。优先复用 JobQueue、已有 provider settlement、workflow correlation 和恢复扫描。

需要分别证明：已完成节点不重做；审核等待跨重启仍等待；已知 provider 任务优先查询和收货；进程内 turn 无法续跑时诚实进入对账状态，之后通过明确恢复动作继续。

run 幂等键只能防止重复建 run，不能自动保证视频提交等外部副作用恰好一次。提交结果不明时，如果 provider 没有可验证的幂等或查询机制，禁止盲目自动重发。[S4]

### 7.2 必做真机场景

在隔离测试项目、可控制的后端进程完成以下演练：

1. attempt 已持久化、正式任务尚未派发的窗口中断，重启后判断是否确实未提交，再安全继续。
2. 已关联 AgentTask 的 turn 中断，重启进入对账；不能仅凭“未完成”再发一个同目标 turn。
3. 真视频已有 provider ID 后中断轮询，重启按 ID 查询和收货；不能重新生成来假装恢复成功。
4. 在 `waiting_human` 时重启，原审核对象和意见仍在；审核通过只启动一次下游。
5. 审核通过后、下游派发附近中断，重启对账，下一节点不丢失也不双发。
6. 两个重复启动请求、两次同意点击或网络重试，核对唯一 run 和唯一相应 attempt。
7. 停止运行后，真长任务结果晚到；可以留存隔离候选和回执，但不推进原链、不自动选片、不把 stopped 改 completed。
8. 提交响应不明的受控故障；如无法确认提交结果，留 `needs_reconciliation` 和可操作说明，不猜测“肯定没生成”。

可以用注入点精确控制故障窗口，但必须实际终止并重启测试后端，至少视频收货和审核等待用真实任务。单测模拟不能代替全部真机恢复。

### 7.3 故障后的修复边界

停止后重试是新 attempt 或新的 run，必须留原关联与明确意图。新候选版本不得覆盖旧版；原已完成节点可以核验后保留。

如果审核驳回导致 run 停止，先在独立 W06 修复，再由用户复制或修改流程发起新运行，并明确复用已有合格产物。这是本轮人工驱动的迭代方式，不宣称自动返工循环已实现。

每个错误显示具体缺项和下一动作：缺批准 Look、缺选片、素材过期、任务结果不明或非法模式。不要只显示“失败，请重试”。

## 8 F 批 冻结和三轮独立生产复验

### 8.1 冻结内容

冻结最终代码提交与工作区 diff 标识、模板版本、Agent 配置、正式 Skill 版本与全部加载内容 hash、模型配置和本轮测试夹具。

Skill hash 必须覆盖真实加载的内容，包括执行决策所依赖的 reference 文件；只保存一个主文件 hash，却从变化的 references 目录加载新规则，不算冻结。

旧 run 使用冻结内容或在内容不可取得时明确阻塞，不能看到 hash 不一致仍加载新文件。新 run 使用新定义和新 Skill，两者证据分开。

### 8.2 三轮复验安排

| 轮次 | 项目和目标 | 重点 |
| --- | --- | --- |
| F1 | 新项目、新会话，从新故事到六员成片 | 完整主链、实际双审核、真实媒体和两 Skill 的对应独立用例 |
| F2 | 另一新故事，沿同一冻结模板生产 | 迁移、同 Agent 多节点、正常切镜和连续动作判断 |
| F3 | 独立生产任务，包含合法既有资源复用、真实中断收货及装配 | 复用、重启、精确版本交接、不重复生成 |

每轮都需要实际六类 Agent 的职责结果和新视频、成片；F3 可以复用已经批准的资源，但必须如实标明，不把它称为从零新建全部资产。正常复用应成为能力证据。

冻结前 D 批集成测试不自动算 F1。每轮新建受测会话和独立运行，不将不同基线的好片段拼成一次通过。

中途修改代码、模板或 Skill，先修复、重新冻结，再重新开始计数。保留之前失败轮的归因及候选，不从报告里删掉。

### 8.3 不设置虚假的模型保证

三轮通过只说明所记录样本与条件下可用，不证明任意动画题材、任意镜头复杂度或其他 provider 都稳定。

分别记录第一候选可用率、通过工程验证的任务比例、重试次数、工具错误、人工介入、完成耗时和待评数量。明确分母和样本范围，不只展示最好的一次。

## 11 测试记录和失败处理

### 11.1 证据最低要求

每个真实运行保存：projectId、workflowId 与 definition revision/hash、runId、nodeId、attemptId、AgentTask ID、Skill 内容依据、实际 model/thinking、目标范围、实际输入版本、输出、用户决定、事件和结论。

视频另保存 provider task/video ID、脱敏请求、查询结果、生成依据、候选版本和首中尾帧。成片另保存 Sequence 快照、旁白音频、音乐素材、render 状态及探测结果。

证据索引进入项目可持续保留的位置；不要所有真机脚本、结果和截图都只留未入库临时目录。遵守仓库约定，将可复现且无秘密的测试脚本与索引纳入版本管理，媒体放项目既有资产位置。

### 11.2 修复顺序

发现失败后按以下顺序判断第一处偏离：

1. 目标、输入范围和审批前置条件。
2. canonical、具体版本、资源绑定与 freshness。
3. Skill 是否正确加载及 Agent 方法选择。
4. adapter 编译、provider 模式和参数。
5. provider 生成候选本身的随机质量。
6. 回执、truth gate、完成校验和工作流交接。
7. 审核、选片、装配和前端状态投影。

保存失败样本，先修负责该问题的最小层。定向验证通过后再继续主生产。一次候选失败不自动等于引擎失败，也不能把确定性的接线缺陷推给模型随机性。

### 11.3 评测不能只有日志绿灯

本轮同时验证运行轨迹和环境最终状态：工具实际调用了什么，canonical 与任务账本最终是什么，媒体是否存在且可观看。工程检查、模型筛查和用户看片各承担适合的判断，不互相替代。[S8][S9]
