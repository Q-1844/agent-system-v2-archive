### 0.3 本阶段必须守住的十条规则

1. 一个画布 Agent 实例对应明确的真实任务范围；聊天回复“完成”不能决定节点成功。
2. 工作流决定何时派发；现有专业 Agent 和授权工具决定如何制作与写 canonical。
3. 同一阶段只能有一个派发权威，不能让工作流与 Producer 各自执行完整默认链。
4. 执行连线既表达先后，也必须有可检查的数据交接；不能把上一篇聊天记录当作唯一输入。
5. Skill 只绑定，不单独运行；绑定版本与实际加载内容需要一致。
6. 人工审核针对具体产物版本；“工作流通过”不能默认等同于资产批准、正式选片或 `final_render` 定版。
7. 草稿可改；正在运行的定义、Skill、模型配置快照不可被草稿编辑静默改变。
8. 已提交的任务先查状态、再收货；提交结果不明时不盲目重发。
9. 刷新浏览器、断开事件流、进程重启，不得制造新任务或丢失待审核状态。
10. 未通过的路径如实阻塞；不使用 mock、执行脚本或截图冒充正式 Agent 跑通。

## 2. 最小后端结构

不要替换当前 Agent 系统，也不要引入 Langflow／LangGraph 作为新运行依赖。参考其机制即可；复用项目现有 Python 后端、数据库、任务服务、委派 Bridge、session governance、OCC、locks、receipts 和 truth gates。

实现可收束为三个服务职责，文件如何分拆由仓库风格决定：

| 职责 | 做什么 | 优先复用 |
| --- | --- | --- |
| 定义与校验 | 读取目录、保存草稿、后端校验、编译顺序计划及绑定 | 现有 registry、schema、权限检查、数据库 |
| 顺序执行与任务适配 | 建立 run、派发一个节点、收货验证、审核等待、继续与停止 | 正式任务入口、Producer 委派底层服务、已有后台 worker |
| 查询与前端投影 | 查询 run、节点／attempt／任务／产物／审核、事件订阅或轮询 | 现有任务事件、查询 API、日志与 UI 组件 |

逻辑持久化至少覆盖“工作流定义”“运行及节点状态”“事件／审核决策”。它们不必各建一套系统：可复用既有任务、审批表和事件表，或在现有数据库增加少量表与 JSON 快照。关键是事务、唯一性和跨重启保存，而非表的数量。

不要新增 Redis、Kafka、独立微服务或通用插件执行框架来解决一条顺序链。不要用 localStorage、进程内字典或正在打开的浏览器连接作为正式运行的持久化来源。

## 4. B 批｜定义契约、保存、校验与编译

### 4.1 延续 `workflow_draft_v1`

先读取现有契约，不擅自更名或强推 `v2`。若需增加执行字段，用有明确默认值的兼容扩展；旧草稿缺少必需运行字段时，保存与编辑仍可用，启动时报具体缺项。未来不兼容格式需显式迁移，不静默推断。

新增运行必需字段，应尽量放在现有 Agent 配置／契约面板中：

- 本节点任务目标与范围：例如指定故事段、资源集合、镜头集合、Sequence；不能只写“调用导演”。
- 必需输入的来源：启动输入、上游产物引用或已有 canonical 版本。
- 预期产物与节点完成条件：候选、批准资产、已选视频或可审 render，依据真实工具契约选择。
- Skill 绑定与版本；已有工具的受控选择。

“添加一个 Agent 卡片”与“形成一个可启动的任务”是两件事。没有目标或素材范围时，允许保存草稿，但启动必须指出缺少什么。

### 4.2 后端保存与冲突保护

保留 localStorage 作为离线草稿／备份，但真实 run 必须基于明确提交给后端且通过校验的版本。保存返回工作流 ID、服务端 revision 和更新时间；客户端提交预期 revision，冲突时保留本地修改并提供重新加载／另存副本，不能后写无声覆盖。

旧浏览器草稿只在用户主动保存或运行时导入。导入必须保持 node／edge ID、Skill 引用、人工审核内容及坐标。后端保存失败时仍显示未保存，不能切成“已同步”；启动响应超时时先查询相同启动键对应的 run。

### 4.3 后端校验比前端体检更严格

前端 `connectionRule/validateDraft` 继续用于及时反馈；后端是运行准入权威。校验错误返回 node／edge ID、字段和可执行的修正理由。

最少检查：

1. schemaVersion、项目归属、node／edge ID 唯一、悬空引用。
2. 注册 Agent／Skill／工具存在且正式可用，版本可定位。
3. Skill 只能接 Agent，没有执行端口，绑定适用且未重复冲突。
4. 执行图无环；忽略节点坐标，仅按合法执行边编译。
5. 首版支持一条连通的顺序链。多个起点、多个终点、分叉或汇合给出“不支持此结构”，不能按数组或横坐标猜运行顺序。
6. 无执行边的单个 Agent 流程可以运行；审核不作为独立入口。孤立的额外 Agent／审核是错误；只有视觉边界不能运行。
7. 人工审核有具体上游审核对象及可识别的决策权限；连续审核合法。
8. 节点任务范围、输入契约与上游产物类型兼容；缺少时不能用自由文本蒙混通过。
9. 核心工具不可减；额外工具必须已获授权；用户串接 Agent 不改变 ownership。
10. 当前项目所需输入可读，必需批准／选片状态满足；可在运行中形成的输入先验证结构，派发前再验证实际产物。

开始／结束是纯视觉节点：不生成 task，不代替项目输入或产物，不由位置定义真实首尾。若现有格式有边界装饰连线，按原契约单独保留，不能把它算成执行依赖。

### 4.4 编译结果

产生一份可以审查的计划：有序执行 node IDs、每个节点的任务范围／输入来源／完成条件、Skill 绑定、审核对象、所解析的模型与思考配置、预计真实调用类型。不给 LLM 重新解释节点顺序的权限。

结构编译应是确定性过程，不为编译整个图再调用模型。复杂自然语言仍由搭建助手解析为草稿操作，与编译和运行分离。

### 4.5 启动快照与输入版本

启动时固定：工作流定义 revision／内容 hash、节点实例及范围、Agent 注册基线、Skill 内容版本／hash、工具授权集合、文本模型与思考参数、当前媒体 Provider 配置标识。

固定 Skill 不能只存一个已无法取回内容的 hash：保存允许使用的内容快照，或引用能跨重启读取的不可变 git／资源版本。部署或 Skill 文件变化后恢复旧 run，先确认原基线仍可执行；不能读最新文件并声称仍在使用旧版。无法维持旧基线时，保留原任务收货与证据，明确从新基线开启后续尝试或新 run。

同时记录启动输入版本，并维护**逐节点输入／输出版本账本**。不能把“启动时项目 revision”永远锁死：前面 Agent 正常写入的新故事／资源／镜头应成为后续节点的受控输入。派发前解析确定的上游输出和所需 canonical，记录该节点实际使用的版本。

外部任务或用户修改了某个必需输入时，按 freshness／OCC 处理冲突；不把工作流内部预期的新产物误判为外部冲突。也不让后续节点随意读取“当前最新候选”而忽略已批准的输入引用。

## 5. C 批｜接通六个 Agent，并解决重复委派

### 5.1 只有一个顺序调度权威

工作流 run 负责选择下一节点，并通过现有正式任务服务派发。Producer 保留其专业规划、协调和工具能力，但在工作流上下文中，不能越过审核或擅自调用尚未获准启动的画布节点。

优先方案：复用当前 Producer 委派底层服务；为其增加可验证的 workflow 上下文，至少含 run ID、node ID、任务范围和允许派发目标。当前节点中的必要子任务依然可以走既有机制，但必须归属当前 node，遵守审核及 ownership。

对 Producer 放在链首的默认模板，将其范围明确为本次制作计划／交接准备，后续专业节点由顺序执行层派发。若现有 Producer 会自动全链委派，必须用**服务端限制**约束其派发范围，不能只靠提示词“请不要多做”。

不能限制时，先修最小控制入口。禁止把 Producer 自动生成的五个子任务，再加上画布的五个节点，统计成六员接入成功。

Producer 不是每条流程必填。只包含“装配 Agent＋审核”的合法子流程不应为了运行而偷偷增加一轮 Producer 制作；若底层正式权限需要 Producer 的委派服务，复用该服务而非另起一个未经用户配置的自主规划 Agent。

### 5.2 每个 Agent 都经过同一生命周期适配

适配层统一以下语义即可，函数名沿用项目惯例：

- 解析本节点输入和权限，读取 canonical／上游 artifact refs。
- 建立任务尝试和派发关联，调用真实 Agent 入口。
- 保存真实 task／session／provider task 关联与 receipt；处理等待状态。
- 收货后校验实际产物与完成条件；形成交接包。
- 失败、人工等待、结果未知、取消请求与恢复分别处理。

不要重新实现专业 Agent 的制作策略，或直接从 workflow service 写故事、资源、镜头和 Sequence。修复入口适配问题可做最小改动，保持原 Agent 聊天入口可用。

```json
    }
  ],
  "brief": "供下游理解的简短说明，不能代替真实产物引用"
}
```

执行边只需要引用这个交接，不新增第三种线。对于更早节点的故事／资源，按明确的项目引用和已完成节点输出解析，不要求单根执行边承载项目全部 JSON。输入映射采取有限的已有字段／类型选择，不建设任意表达式语言。

节点成功必须满足：正式任务的真实结果＋必要 receipt＋产物存在且属于正确项目／范围＋契约要求的状态＋完成校验。工具返回 accepted、LLM 结束、或者 generation task 已提交，都不能单独算节点成功。

已有批准素材的复用，标为复用并保留源版本与 basis。正式链中某个 Agent 真正运行但只读取／核验既有素材，可以作为复用测试；**不能替代至少一次该 Agent 真实制作新产物的验收**。

### 5.4 默认模板只是起点

根据真实输入契约，提供可解释的默认顺序。候选示例是 Producer→编剧→资源→场景→导演→装配；仅在仓库确实支持这种顺序时启用。

需要批准 Look、场景或视频选片时，将既有等待 gate 正确呈现，或在相应位置加入人工审核。导演若只能产出候选，后面不能直接宣称装配已拥有正式选片；必须等待用户选择，或明确使用系统允许的候选粗剪模式，不能混淆。

每个模板说明：要生成什么、要哪些输入、哪一步需要用户、最终得到候选还是已定版作品。用户可修改顺序，但后端按输入契约判断是否能运行。

## 6. 全测试文本模型开启思考模式

### 6.1 模型范围

按用户报告，六个 Agent 文本模型统一为 `agnes-3.0-flash`，配置从 `config.yaml` 单点解析。本阶段先核对实际结果，并把**开启思考**补进当前统一的调用配置／适配链。

覆盖六员的文本推理、搭建助手的 Producer 复杂解析、规划、文本质检、失败诊断、工具调用后的继续请求和重试。不要以“这是 JSON 解析／简单任务”为由关闭思考。确定性本地规则、编译和结构校验本来不调用模型，不需要制造思考调用。

报告指出 Director Vision 的 2.5 不在此次文本模型切换范围。保留其既有视觉 Provider 和路由；若它的某个分支实际是文本规划调用，也要从统一文本链进入思考模式，不要因为配置名叫 vision 就漏检。图片、视频、TTS 模型不按文本字段强行改写。

### 6.2 官方已确认的参数

Agnes 官方文档 [S1] 给出 Chat Completions 的启用方式：

```json
{
  "model": "agnes-3.0-flash",
  "chat_template_kwargs": {
    "enable_thinking": true
  }
}
```

这是请求片段，需要与项目真实 `messages/tools/stream` 等字段合并。若项目用 OpenAI SDK，检查这个扩展字段是否需经 `extra_body` 传递；关键是**最终发送到 Provider 的 JSON 中出现该字段**，而非内部配置中出现。

若现有正式入口采用 Anthropic 兼容 Messages，官方另给 `thinking.type="enabled"` 与 `budget_tokens`。预算必须结合真实端点、最终输出预留与实际成功请求核验，不照抄官方示例中恰好相等的 `max_tokens/budget_tokens`，也不迁移端点来绕过当前适配问题。Responses 入口的思考字段不得凭兼容名称猜测。

本次核验的官方页面未把 `reasoning_effort=high/max` 列为必需参数。可以在**实际 Provider 文档与成功探针确认后**增加最高适用强度；不得用这一字段代替已确认的 `enable_thinking=true`，也不要把第三方列出的档位当成官方契约。

### 6.3 必须交付的证据

每次真实文本请求记录：agent／用途、run／node／attempt、模型 ID、端点类型、思考启用参数的脱敏快照、配置 hash、Provider 响应 ID／finish_reason、工具调用结果和可用 usage 元数据。

检查思考参数在首次请求、工具回填后的请求、错误重试、恢复后的请求中没有丢失；不能在参数不兼容时自动回退到关闭思考并继续报测试通过。

不要求模型公开完整内部推理，不把隐藏推理写入用户界面。若 Provider 返回 reasoning usage，可记录计数；不返回时以官方契约、实际出站参数与成功响应记录“已请求开启，内部使用量未暴露”，不能虚构 token 数。

思考、文本、工具参数是不同通道。检查流式工具参数拼接、空文本块、仅工具调用的响应、截断与 `finish_reason`，避免把 reasoning／thinking 文本错误拼入意图 JSON或最终正文。

## 7. D 批｜运行、人工审核、停止与恢复

### 7.1 状态可以沿用现有枚举，但必须表达这些区别

| 语义 | 说明 | 后续行为 |
| --- | --- | --- |
| 待派发／就绪 | 尚未调用当前节点 | 只有前置满足才能派发 |
| 运行中 | 已关联真实任务 | 查询同一任务，等待结果 |
| 等待人工 | 画布审核或 Agent 内部既有 gate | 展示对象与具体决策入口 |
| 等待外部 | 视频／图片／TTS 等仍在运行 | 保存 task ID，不以超时当失败重发 |
| 需要核对 | 提交是否成功不明／输入过期等 | 禁止下游，先 reconciliation |
| 失败 | 已确认不可继续，附错误来源 | 用户修复后显式重试或另开 run |
| 驳回停止 | 用户拒绝审核 | 不自动回环、不继续派发 |
| 停止请求中／已停止 | 不再派发；在途任务按真实能力处理 | 保留收货和关联记录 |
| 成功 | 产物通过本节点完成校验 | 唯一启动下一节点 |

run 的总状态必须由节点状态和真实任务推导。`waiting_human`、`needs_reconciliation` 与 `failed` 不可全合成“运行中”。完成整条链只证明按定义交付了相应产物；不自动证明用户已定版。

状态变更与对应事件在同一数据库事务或现有可靠 outbox 中保存。审核决策落地与“允许下一节点就绪”也需保证可恢复一致性；worker 根据持久状态领取，不因 HTTP 响应丢失遗漏继续。外部调用及 canonical 写入仍经既有工具和回执核对，不把一条自写事件当作事实完成。

### 7.2 人工审核

审核申请持久化：run、node、上游 attempt、精确产物引用／版本／必要内容 hash、审核说明、权限、申请状态、决策时间、用户身份、意见和决策 receipt。

卡片中的“审核者：制作人”只是展示标签，不是权限凭据。首版可使用项目现有拥有者／授权用户权限；没有账户体系时采用项目现有用户专用入口，不新建组织角色系统，但仍不能让文本模型伪造用户批准。

审核动作区分：

- 流程继续许可：允许下一个节点开始。
- 资源正式批准、视频 select、最终 render select：走已有 canonical／用户专用入口。

UI 可以在同一面板引导完成二者，或组合调用已有正式入口并分别保留回执；不得把一个通用 `approved=true` 自动写成所有资产已批准或 `final_render` 已改变。

两个连续审核是两个独立申请与决策。第一轮通过后第二轮仍等待；第二轮拒绝则下游停止。二者可审核同一组不可变产物，但说明／意见分别存档。

审核提交检查待审状态、预期版本和对象。重复点击同一决策返回已处理结果；相反决策、旧审核、错误节点／项目或无权用户不得覆盖先前决策。

审核对象在等待期间被修改或替换时，旧意见保留为历史，标为对当前对象过期，不沿用到新对象。不要因无关项目字段变化而让全部审核失效，应以审核对象及其必要 basis 判断。

### 7.3 幂等与两类重试

启动请求应有幂等键，且绑定项目／用户／工作流版本／启动参数摘要。同键同参数返回同一 run；同键不同参数返回冲突。双击运行、客户端超时、刷新页面不能创建两份生产。

节点派发建立唯一关联：run＋node＋attempt。使用已有正式任务的 request key／client task ID 或等价机制，把派发与 task 关联写入可靠存储。worker 领取使用数据库 CAS／现有租约，避免重启后的两个 worker 同派发。

区分：

1. **网络重试／状态恢复**：查询已有任务、重连事件，不生成新 candidate。
2. **重新制作候选**：明确创建新 attempt，保留原候选和 basis，按真实工具策略重新生成。

外部 Provider 不支持幂等时，无法仅靠本地状态宣称 exactly-once。对于“Provider 已可能接受、但本地没拿到 task ID”的窗口，进入需要核对，利用现有 correlation／请求记录／正式查询能力找回。无法找回时显示不确定性并等待明确处理，不盲重发。

### 7.4 重启恢复的最低要求

恢复时加载持久化 run 快照、节点状态、attempt 和真实 task 关联：

- 已完成的节点不重做；从其已验证的产物版本继续。
- 运行中的既有任务重新查询／关联，保留原 task ID。
- 人工审核仍等待同一申请；已经决策的申请不再弹成未决。
- 尚未派发的节点，前置仍有效时可以显式继续。
- session 被既有治理标记中断且不能恢复的，保持真实中断；若需新 attempt，从明确检查点启动，不能声称恢复了原 turn。

工作流 lease 与资源锁分开。等待审核时释放不再必要的短期制作锁，保留输入版本；恢复时重新校验 freshness 并按需取得锁，避免人审卡住整个项目数小时。不能为了续跑跳过 OCC。

### 7.5 停止与晚到结果

停止后立即禁止后续派发；对已有任务仅使用真实可用的取消接口。Provider 不支持取消时显示“后续已停止，已提交任务仍可能完成”，继续保存晚到结果与关联；不能声称远端计算已停止。

晚到结果不能把停止／驳回的 run 改成成功，也不能覆盖新 attempt、已选版本或 `final_render`。候选保存、canonical 更新是否有效，遵守已有任务和 OCC 机制。

## 8. E 批｜最小 API 与前端真实运行视图

### 8.1 API 语义表

这是一组功能语义，不规定已有路由必须改名。复用或实现后，补充真实 method／path／请求响应样例。

| 操作 | 最小要求 |
| --- | --- |
| 读取组件目录 | 真实六员、Skill、版本、契约、权限和可用性 |
| 保存／读取工作流 | 项目隔离、revision、旧草稿兼容与冲突保护 |
| 校验／编译 | 无执行副作用；返回问题定位或可审顺序计划 |
| 启动 run | 引用已确认定义／参数、幂等键；尽快返回已持久化 run ID |
| 查询 run | 总状态、节点状态、attempt、task refs、产物、错误和待审 |
| 审核决策 | 用户权限、对象版本、一次有效决策、继续或驳回停止 |
| 显式继续／重试 | 区分已有任务恢复与新 candidate；检查版本与状态 |
| 停止 | 禁止下游；报告在途任务实际取消能力 |
| 事件查询／订阅 | 单调序号、run／node／attempt 归属，断线后能恢复观察 |

所有查询、保存和校验都不能派发生产任务。启动、审核和继续的有效操作才可能推动执行。

错误响应区分结构／版本／权限／前置素材／Provider／任务中断／未知提交，给出原始分类及可读说明；不能将所有错误改为 200 并只在聊天中解释。

### 8.2 前端改动只服务于接入

保留当前风格和布局，不开展新的视觉设计阶段。最少补齐：

- 保存状态：本地修改／后端已保存／冲突。
- 运行状态与当前节点、任务引用、产物入口和具体错误。
- 审核对象、两轮意见、通过／驳回按钮及已有选片／定版入口。
- 恢复观察、继续／重试与停止；按钮随真实状态控制。
- 当前 run 与可编辑草稿分离：草稿编辑不能改当前快照。

运行中的节点颜色与说明由后端状态映射；不以计时器、消息关键词、请求 resolve 或线条动画推断成功。一个节点在等内部用户 gate 时，不可显示它已完成然后另行等画布审核。

`linked_task_ids` 在草稿编辑期间仍为 0；真实 run 的任务关联显示在运行数据中。不要把它塞回草稿触发已有“后台任务引用”清理逻辑或误报。助手说“运行这条流程”也不能自行执行；可提示用户使用运行按钮。

### 8.3 事件与断线

优先复用现有事件设施；没有可靠事件流时采用 run 状态轮询即可，不为“流畅”强行引入 WebSocket。关闭页面不取消任务，建立事件连接不启动任务。

状态快照带版本／事件游标。处理获取快照与订阅之间的空隙：从游标补事件，或定期重新校准状态。去重并忽略旧 attempt 的过时事件；发现序号缺口时重新取快照。跨 run／跨项目事件不得污染当前画布。

前端断线显示观察连接问题，后端任务继续按真实状态运行。后台标签页重新激活后要拉取状态，避免浏览器计时器降频造成假死。

沿用现有 Agent 工具循环、超时和退避策略，为失去进展的任务保留明确的诊断与停止出口；不要用无限重试保持假运行。429 按服务提示退避；超时后先判断外部是否已接受，再决定查询、等待或新尝试。额度充足不意味着放弃任务生命周期控制。

### 8.4 保护此前修复

保留显式 Vue Flow store ID，编辑／运行的 store 避免串用；加载 dimensions 为 0 的自愈逻辑、坐标转换、审核图遍历、删除后重建的执行顺序、失败操作不列成功摘要等不得回退。

多标签页保存由后端 revision 解决；带数量删除与清空审核内容是现有助手限制。仅在影响本次接入时修复，并加定向回归。否则准确展示限制，不为凑功能全绿扩大前端重做范围。

## 9. F 批｜真实 Agent 测试与修复循环

执行配套测试书，至少包括六员分别制作、两节点交接、真实 Skill 绑定、双审核、六员新项目整链、故障恢复和冻结后的新会话复验。

zcode 可以编写测试驱动、故障注入、数据库核验和媒体检查脚本，但**制作策略、正式写入和生成应由系统 Agent 通过实际运行入口完成**。不能在测试脚本里直接创建故事／视频／Sequence，再把它们算作 Agent 自主成功。

图片／视频／TTS 调用充足测试；记录调用目的、候选与问题。每次修改后先跑失败项与受影响链路；通过后再做对应新会话复验。不以额度多为由盲重跑同一请求，也不以额度少为由取消必要真实测试。

发现问题按层归因：画布／草稿→API／契约→顺序执行与状态→正式任务适配→Agent 决策／Skill 加载→Provider／媒体质量→canonical／审批／版本。先修有证据的层，不把所有失败都写进视频 Skill。

需改 Skill 时，先证明是通用规则或加载问题；最小修复、版本化并重新冻结。盲测中途修改的 run 不纳入修改后版本的通过次数。

最终报告建议保存到 `docs/workflow/PHASE46_WORKFLOW_INTEGRATION_REPORT.md`，证据路径按项目既有惯例。必须包含：

1. 六个 Agent 真实入口／核心工具／ownership／完成条件与实际 task 对应表。
2. 定义保存／revision／运行快照／数据交接／审核／恢复／前端投影的实现路径。

4. 测试分组和轮次，首次失败、修复后结果、真实生产与模拟故障的边界。
5. 至少一个六员新项目：run、节点、task、receipt、canonical／媒体版本的贯通索引。
6. 浏览器截图或录像、逐镜视频、可审 render、旁白与音乐检查结果。
7. pending 的真实用户批准／选片／final 状态与可观看材料；不冒充用户定版。
8. 未完成项／回归失败／限制、恢复能力范围及实际基线 commit。

## 11. 可直接交给 zcode 的开工指令
