# 协作系统 R1 首轮修复报告（历史记录）

本文件保留首轮范围与验证结果；当前交付为 R1.1，最新改动和验证结论以 `03_最终审查与完成范围.md` 为准。

## 1. 结论与本批边界

我已经直接修改源码，沿用深度研究提出的方向：执行与审核重叠，错误分支独立处理，决策交给 Producer；先确保并行执行时，结果不会重复提交、覆盖旧版本或被错误验收。

本批完成了并发写入保护、生成与恢复安全、严格版本审核，以及 Producer lead 正常执行路径中的持续并发审核。**尚未实现可独立执行的子 Producer + 过渡池，也未实现持久化依赖图的自动下游派发。** 现有 `decision_requests` 是结构化决策记录，不是已经运行的子 Producer 或结果池。不能据此宣称全部协作模式已经完成。

## 2. 已经修改的关键行为

| 问题 | 本批处理 | 具体意义 |
|---|---|---|
| 多个任务各自读写整个项目，后写覆盖前写 | ProjectStore 增加进程内/跨进程锁、事务及已加载快照的签名检查；批准后的创作态提交显式检查原签名 | 对经此入口的写入避免静默丢失更新，冲突需重新读取处理 |
| 视频下载结束时输入已变化 | 在最终挂接事务内重新检查输入签名及原有 native 条件 | 变化中的旧结果保留为未挂接产物，不直接成为当前视频 |
| 新视频覆盖固定文件，旧版本指向被改写内容 | 新视频使用带版本标识的独立文件路径；重复回调不改变已有选中版本 | 新版本产物保持独立，重复消息不会抢回用户选择 |
| 提交结果不明时自动重复 POST | 提交意图先持久化；超时、模糊 5xx、无效回执进入 uncertain；已知 ID 走恢复路径 | 减少重复付费风险，结果不明时等待核对，而不是盲目再生成 |
| 任务队列损坏被当成空队列；取消窗口留下假运行 | 损坏时保留原文件并要求恢复；记录 handler 启动状态并处理取消窗口 | 新协议中确认尚未开始提交的任务可重新排队，旧不明任务保持保守处理 |
| 主控租约异常时仍允许执行 | 租约获取/转移/验证受锁保护；缺失和代际不符时拒绝 | 明确主控权限，避免将异常解释成允许执行 |
| 缺帧、视觉调用异常、审核维度缺失仍可能过关 | 单镜头隔离失败；审核结果绑定视频版本和输入签名；显式版本缺文件不回退到别的视频 | 缺证据时标为 incomplete/stale，不能冒充机器通过 |
| 修复任务失败却继续审核旧版本 | 修复需 DONE、新版本、来源匹配和对应版本审核回执 | 防止“没修成功却通过了旧视频” |
| 身份问题靠重复抽卡；相同硬错误持续消耗 | 身份错误直接提出策略决策；相同硬错误在一次重试后请求改变策略 | 为 Producer 留出明确决策点，减少无效重复 |
| 全部执行结束后才统一审核 | Producer lead 执行期间观察可审核版本，以有界异步并发进行审核，最终复用仍有效的回执 | 缩短审核尾部等待；限制审核并发，避免无限请求 |
| 完成状态掩盖问题 | 增加 completed_with_issues 展示，区分机器判定与用户验收 | 结束不再等于所有问题解决 |
| 对话解析小错误导致多轮失败 | 支持精确角色名后的括号提示，明确无对白标记；提交前批量收集确定性错误 | 一次反馈多镜头问题，减少排队后才发现输入错误 |

## 3. 并发究竟做了什么

已做的是：审核任务与 Producer 执行阶段在时间上重叠；不同镜头的视觉审核使用有界异步并发；帧提取从事件循环移到线程；文件写入与主控租约提供跨进程互斥能力。审核并发上限在当前组合策略中为 2。

这不等于启动了多个拥有完整工具权限的子 Producer。也没有把生成服务的队列容量自动改大。恢复入口还没有完全接入同样的持续审核路径，不能把正常路径的并发效果推广到所有模式。

## 6. 明确保留的限制

1. ProjectStore 的保护覆盖本批改造的公共入口。直接绕过该入口的文件写入、其他资产存储和新构造对象的保存，不因此自动获得完整 CAS。不能宣称全系统线性一致。
2. 租约保护和委派工具入口校验，尚不等于所有专家异步操作在最终提交点都有统一 fencing；子 Producer 落地前还应补齐。
3. 没有 Provider 幂等键/按意图查询能力时，无法从客户端保证 exactly-once。uncertain 必须核对，不能把普通失败重试当作恢复办法。
4. 已被旧代码覆盖的历史视频，无法靠修改路径自动找回；新路径保护后续产物。
5. 未开展真实效率对照，因此目前只能确认机制成立，不能给出“提速百分之几”。
6. Windows 文件锁及本机 Python/依赖组合需要本机验证。SFC 编译不替代完整前端构建。

## 7. 下一批建议：把子 Producer 权限真正用起来

保留你提出的大权限方向：子 Producer 在被分配的工作域内可以直接切换 skill、执行和生成，不必逐步向总 Producer 请示；执行产物默认写过渡池。权限大应体现在可独立完成工作，而不是直接争写正式项目。

下一批应配套实现以下模块后再放开并发：

1. **过渡池对象与落盘协议。** 记录 task/run/parent、输入基线、产物版本、审核回执、状态和成本；候选与正式选中版本分开。
2. **提交协调器。** 审核与执行并行；达到正式接纳条件时，在统一提交入口校验输入基线、租约代际与版本，再原子接纳。已过期候选保留供比较，不直接覆盖。
3. **子 Producer 执行入口。** 注册可切换 skill、工作域、预算和决策权限；只有跨域修改、预算增加或冲突决策升级到总 Producer。
4. **持久化依赖调度。** 完成事件驱动可运行节点；重启后恢复；明确幂等键、取消传播、失败隔离与背压，避免后台轮询长等。
5. **恢复与项目身份隔离。** 先定位本批全量的 child 数量差异，给测试使用独立目录/标识并可靠收尾；再扩展到项目删除重建、旧任务迟到和跨代恢复的生产保护。
6. **效率实验。** 固定相同输入与 Fake Provider 耗时，对比串行、审核重叠、多个子 Producer + 过渡池；记录总墙钟、关键路径、依赖空等、审核尾部、重复请求、冲突率和人工介入次数。真实配额恢复后只补少量真实任务验证。

适合的实验故事仍可用“突入怪物要塞”的动作场景和“室内讨论古生物、有人端起茶杯”的交流场景。它们分别覆盖独立镜头并发、连续性依赖、多人台词、道具动作及审核回执，剧情服务于测试，不把画面好坏作为本轮效率结论。

当前不需要你再作架构方向选择。先通过本机回装检查与恢复差异定位，再按上述顺序进入子 Producer/过渡池批次，比仅修改权限提示词更容易验证。
