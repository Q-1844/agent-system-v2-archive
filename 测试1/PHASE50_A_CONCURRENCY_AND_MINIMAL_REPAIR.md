# Phase 50 A｜最小修复、并发探针与耗时归因

## 1. 目标与范围

回答“我们为什么慢，以及哪里能并行”，随后进入 B 的实际作品制作。优先复用现有异步任务设施、正式工具和资源治理；不扩建新的 Agent、不重写可视化工作流产品、不把本批变成通用调度框架工程。

先核验已有实现。如果已支持分离提交与收货，就直接测；如果只缺一个局部等待点，做最小修复。如果并发依赖大改，交付串行可用方案与具体后续设计，B 继续运行。

## 2. A0：建立真实基线

记录代码提交、六员注册、正式工具、模型 ID、key 类型、工作流版本、候选 Skill 原始文件及完整目录哈希。API key 仅记录类型与脱敏标识。

从上一轮日志与真实失败任务核查以下线索，不能仅凭旧报告结论直接改代码：

| 历史线索 | 需要查到的证据 | 最小处理方向 |
| --- | --- | --- |
| 执行侧曾补交视频 | Agent 轨迹、实际请求、任务 ID、未完成判定 | 修实际提交、收货或合法复用条件；补交单列为人工介入 |
| Skill 曾被触发词误加载 | 选择记录、解析后绑定、实际加载文件哈希 | 显式版本绑定，避免任务词覆盖已指定包 |
| 首帧合格但视频出现分身 | 原片、保留区间、审查输出、选用记录 | 视频审查结果必须能影响装配与返工 |
| 已提交任务被当成新任务 | 提交响应、恢复日志、轮询字段 | 恢复原任务；提交结果不明时先核对，禁止盲目重发 |

只修确有证据且会阻断本轮的项。修复后冻结一次代码与 Skill；之后每次变化形成新运行版本。

## 3. A1：定位串行来源

查找生产入口、Agent 调用封装、视频 adapter、轮询 worker、项目锁和工作流等待。关键不是操作系统线程数，而是：提交拿到任务标识后，是否仍占用整个项目的长锁并阻止无关任务。

逐项回答：

1. POST 返回后，任务标识是否立即持久化？
2. 工具是否只有“等到完成才返回”的形态，或已有正式 submit/status/collect 等价入口？
3. 同一导演是否因等待生成而停止全部规划和审查？
4. 不同 shot 的候选写入，是否被一个过大的项目锁串行化？
5. Producer 与画布执行器是否重复委派同一个任务？
6. 服务受理、排队、生成与结果下载是否被混为一个状态？
7. 轮询是否正确使用对应模型的查询标识？当前 Flash 官方要求用 `video_id` 配合 `model_name` 查询，而非把 `task_id` 当作检索标识。[S1]

不得为了提速直接删除锁或绕过 OCC。提交阶段占用必要的短锁，远端等待阶段持久记录任务并释放无关写锁，完成后按原 revision 验证写回。遇到版本变化，旧结果可留作旧候选，不得覆盖新事实。

## 4. A2：限流与在途并发分开

维护“提交频率”和“在途任务数”两个限制。整个同类 key 池共用限流器，计入其它会话正在发出的调用。创建多把 key 不用于扩大同类池限制。[S2]

官方 RPM 是参考值，先核对实际 key 类型、端点和执行日响应；当前模型是否沿用 FAQ 的参考池，未证实时不能写为事实。轮询是否占相同 RPM 池也需要查证，不能盲目给所有任务加密查询。

对于不明确的限流反馈，降低频率并记录服务返回的等待指示；持久队列等待，不丢任务。已受理任务继续恢复查询。超时且不知是否受理的请求标记“提交结果不明”，先通过已知标识、请求关联与服务能力核对；不能以本地 hash 假装服务端已保证幂等。

当前模式、价格和能力用现有 adapter 契约核对。本批不新增非法“首帧＋references”的 Agnes 请求，也不为了对齐 Grok 而混用模式。

## 5. A3：渐进探针

选 B 中素材已批准、彼此不读取生成结果的任务。每个任务与真实产物一一对应；可接受结果进入该运行的候选池。

| 探针 | 做法 | 结论范围 |
| --- | --- | --- |
| C1 基线 | 正式入口提交一条，保存全程时间和收货证据 | 单任务耗时与恢复路径 |
| C2 首轮 | 第一条尚未完成时，以合法频率提交另一条独立任务 | 能否保持多个在途任务、是否受理/完成 |
| C3 可选 | C2 无冲突、限流或持续恶化时，测试三条独立任务的在途上限 | 本账号本时段该并发级别是否可用 |

新探针的源视频同样至少 8 秒、默认 10 秒；不要另做短素材绕开本轮时长政策。

C1、C2、C3 的任务若不同，只能作为可行性与观测，不是严格吞吐对照。要比较速度，复用同类规格与冻结输入做串行/并行的小配对，并记录执行时段与服务负载未知项。不要只为凑重复量重生成整部作品。

在途时间重叠只能证明客户端有多个未完成任务。只有服务端提供可信开始/结束状态时，才描述为推理时间重叠。缺少这些字段时明确写“服务端实际并行未知”。

出现拒绝、队列恶化、同槽回执串位或共享资源冲突时回退一级；已受理任务照常收货。若服务端只能处理一个任务，仍可在等待时进行独立规划、素材制作、审查与装配准备。

## 6. A4：依赖决定能否并行

导演先标记真实依赖，调度器只运行就绪任务：

| 任务关系 | 调度规则 |
| --- | --- |
| 独立角色、船、怪物参考资产 | 文字定义固定后可独立制作；合成关系仍需共同检查 |
| 使用同一批准资产但不依赖彼此视频 | 可并行候选生成，分别保存 revision 与 shot ID |
| 必须读取上一镜实际保留端点 | 等该片段完成审查、确定保留区间并获得端点后再启动 |
| 不同机位的正常切镜 | 依据冻结剧情状态独立构图；若实际状态存在未确定分支，则先等待 |
| 上游仍未通过、素材未批准、版本已过期 | 暂不启动对应下游；无关分支继续 |
| 当前 shot 的旧任务结果不明 | 先恢复和核对，不再投一个同意图重复任务 |
| 合格旧片段可正式复用 | 完成条件应承认合法复用，不能强制重新生成 |

本轮不规定所有镜头接尾帧，也不为了并发删除必要接力。执行依赖和共享身份参考是两种关系。

## 7. A5：计时账本

以 UTC 时间戳记录以下事件，并保留同机单调时钟用于精确耗时；跨端时钟不可靠时标注误差：

`run_id、shot_id、attempt_id、模型、Skill 哈希、input revision、ready_at、submitted_at、accepted_at、provider_started_at（可空）、provider_completed_at（可空）、first_completed_poll_at、downloaded_at、review_started_at、review_finished_at、selected_interval_at、assembly_finished_at、human_wait_start/end、request outcome、正式工具 trace、人工介入类型`。

分类报告规划、资产制作、提交前等待、远端等待、下载、审查、返工、装配、人工等待。缺少 provider 时间时，远端等待合并报告，不能凭空拆成“排队几秒、推理几秒”。

报告三类耗时：用户感受到的总墙钟时间、排除人工等待后的墙钟时间、各任务累计工作时间。并发任务的累计时长不能当成整片耗时；阶段有重叠时不能直接相加。用区间并集计算墙钟占用，并记录关键依赖链。

先定义“首次完整可播放候选”与“返工后候选”的终点。等待用户最后看片的时间另列，避免把用户离线时间当模型速度。

## 8. 定向验证与通过条件

只对实际变化做有意义验证：

- 两个不同 shot 同时在途，各自回执正确写入；一个失败不撤销另一个。
- 提交结果不明时不盲重发；已知 task 的轮询失败后恢复原标识。
- worker 重启后恢复已有任务；重复收货不产生第二份正式选择。
- 上游 revision 改变，晚到结果不覆盖新版本；仅实际依赖它的下游失效。
- 原输入合法复用时不被完成判定误判缺视频。
- 含裁切端点依赖的下游在端点可用前不启动。
- Skill 绑定、Thinking、实际模型与输入 hash 可核验。

A 通过意味着本轮能可靠制作、计时真实、并发边界有证据；不要求 C3 一定通过，也不要求画布已支持通用并行节点。输出 A_REPORT、计时账本、实际并发配置、修复提交与仍未知项，随后继续 B。
