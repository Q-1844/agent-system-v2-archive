# CodeBuddy 执行书：系统效率专项优化

默认智能体：GLM-5.3-Flash，开启思考。任务重点是减少不必要等待、重复生产与整轮重启。保留现有六个 Agent、正式 Skill、canonical、OCC、receipts、truth gates、锁和会话治理。

本轮允许根据真实仓库自行选择修法，优先小范围改动；不预设具体文件路径和根因。暂不扩大生成并发，不把模型质量提升设为本轮工程完成的前提。

## A. 核验与冻结交接

1. 阅读本套总控、同步规则和图片验收书。检查项目 AGENTS.md、真实 Agent 注册表、调用链、完成判定、运行状态、限流、参考图托管及正式 Skill 加载机制。
2. 建立独立分支，记录基线 commit、未提交修改和配置指纹。避免覆盖已有工作。
3. 从真实加载入口找到正式 Skill，逐字导出主文件与依赖文件，记录来源、版本、SHA-256 和对应 Agent。Skill 绑定、角色政策和平台参数配置分别标识。
4. 导出已有克苏鲁追船剧本、分镜、角色 Look、船、怪物及相关合格参考。缺什么就记录缺什么；不要从总结文字重建原 Skill。
5. 交接只读副本和 PHASE52_BASELINE_MANIFEST.json，字段包含相对路径、类型、来源、哈希、状态、基线 commit、配置指纹、生成账号的非敏感标识以及已知依赖。
6. 输出 PHASE52_INPUTS_STATUS.md，明确 WorkBuddy 能开始哪些步骤。没有既有分镜时，标明其后续属于自主规划测试。

冻结交接后继续工程工作，WorkBuddy 无需等待本轮修复完成。导出正式 Skill 是读取和复制，不能在交接中默默改写其内容。

## B. 建立可解释的时间线

每条记录至少包含 run_id、task_id、逻辑任务标识、attempt、输入版本、产物版本、事件、时间戳、等待原因、来源与证据位置。敏感凭据不能进入记录。

区分这些事件：输入就绪、排队、等待锁、本地限流、模型请求发出、首次响应、响应结束、生成提交发出、服务端受理、查询发出、查询返回、发现生成完成、素材下载、审查、选版、节点完成和下一节点启动。

服务端真实完成时刻未知时，记录“客户端发现完成”；不能用 API 受理时刻冒充生成结束。文本流式响应的首字节和完整回复也分开。

为每段停顿给出原因：必要上游依赖、等待人审、服务端处理中、模型决策、本地限流、锁、托管、重试退避、未及时调度或未知。允许多个活动重叠，但用户等待总时间只能按时间区间并集计算。

必须同时报告端到端墙钟时间、各活动累计时长和关键路径。不要把“开始到第几个镜头提交”的累计值当成这个镜头自身处理耗时，也不要把重叠活动直接相加作为全天时间。

先用已有日志发现候选问题，再补观测；不能仅凭上一轮解释就认定根因。我们尚未取得的原始日志及报告内容不得虚构。

## C. 有效成果、重试与恢复

完成判定围绕当前输入要求、产物有效性、版本、receipt 和必要审查；“本次是否新增写入”只是一个事件。既有合格成果可完成节点，过期、审查失败或输入已变的成果不能误复用。

| 状态 | 应做的动作 |
|---|---|
| 当前版本有完整、合格成果 | 核验后复用，记录来源，不强迫重做 |
| 已有已受理任务标识 | 恢复查询、下载和收货 |
| 提交超时，是否受理未知 | 保留 unknown 状态，按服务可用的查询或幂等能力核对；无法核对时显式待处理，不能盲目重发 |
| 已明确失败 | 按错误类型修正或局部重试，使用新的 attempt |
| 晚到 receipt | 校验任务、attempt 与输入版本；归档旧结果，不覆盖当前选版 |
| 重复成功回调 | 幂等处理，不重复下载、推进和计费提交 |
| 输入版本改变 | 标 stale，重新验证相关依赖，保留无关的合格成果 |

不要在缺乏服务端支持时承诺跨网络“严格只提交一次”。实际保证应表述为本地去重、已知任务恢复、未知状态不盲目重提，以及无法确认的边界。

针对浏览器刷新、后端重启、网络恢复和 Agent 新会话测试。项目事实从持久状态恢复，不能只靠会话记忆。

## D. 已确定步骤及时推进

导演负责创作与方案选择，系统负责已批准计划的校验、排队、提交、查询、收货与依赖推进。查明哪些模型回合提供真实判断，哪些只是反复读取状态或重复说“继续”。

在现有执行并发上限内改善推进。输入已齐、上游已满足、审核已放行且额度允许的步骤，应通过现有工具或执行层直接推进；需要改变方案、处理新的视觉失败或审批的步骤交回 Agent。

保存计划和任务状态，使失败恢复能定位未完成部分。禁止为了提速跳过身份、环境连续性和重大不合理检查，或取消修复上限、自动放行政策。具体已批准规则先从仓库确认。

真实尾帧依赖继续等待选中版本与实际裁切端点。输入 URL 可访问性、内容哈希及托管状态应可复用核验；失效时局部修复，不能重新创作整轮。图生图重托管若改变像素，不得称为无损复制。

## E. 查询与限流

核对当前账号真实配额、本地配置、请求分类及错误来源。不把官方某个套餐的公开额度直接套给本机，也不把本地拒绝统一叫作上游 429。

有可靠通知机制时优先复用；没有时使用有上限、可恢复的自适应轮询。按任务状态调整间隔、避免同一 job 被多个观察者重复查询，并在服务要求下处理 Retry-After。

查询和创作请求如共享真实额度，需在同一总额度约束内安排，给生产推进留出机会。不能把本地桶拆开后当成上游额度也增加。

轮询变少的同时检查发现完成的延迟。只有减少请求、却让收货更迟，不等于整体更快。

## F. 图片与恢复测试

按 PHASE52_04_IMAGE_TEST_AND_ACCEPTANCE.md 运行现有有意义的检查及新故障场景。真实图片测试固定任务负荷、模型、输入、审核和选版规则；分别记录冷启动与正常恢复，避免用缓存组对比首次生成组。

本轮禁止新增本地系统视频提交。视频恢复可以使用已在档任务查询、已有源素材和隔离的受控回执；模拟结果必须标明，不能宣称真实视频生产提速已验证。

问题修复后运行相关回归，不必无目的反复整轮生产。没有重现的问题按证据不足处理，别为了完成报告编造修复。

## G. 接受 WorkBuddy 建议

WorkBuddy 使用独立快照，提交 WB-EFF 编号建议、出处、失败或成功轨迹、适用前提、可能代价及最小验证办法。CodeBuddy 逐项标为采纳、试验、暂缓或不适用，并给出理由。

正在执行的基线和 WorkBuddy 首次生产不能被中途修改污染。采纳涉及 Skill 改动的建议时另存候选版本；本轮系统修复主线不依赖 WorkBuddy 先成功。

## 交付与验收

输出 PHASE52_CODEBUDDY_EFFICIENCY_REPORT.md、PHASE52_TIMELINE.csv、PHASE52_IMAGE_AND_RECOVERY_RESULTS.md，以及真实修复 diff、commit 和回滚说明。新产物逐份交付。

工程通过需要：被证实的重复生产或推进问题已有修复证据；复用、重启、未知提交和晚到回执不破坏项目真相；真实图片链路正常；同口径计时能够解释优化前后差异。若耗时收益被上游波动淹没，诚实报告“机制改善已验证、提速幅度未确定”。

没有历史同口径运行时，先建立可重复基线再比较，不能把历史粗略总时长和新计时直接相减。不得预先承诺具体倍数或目标小时数。
