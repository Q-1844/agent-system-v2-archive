# WorkBuddy 执行书：按我们的 Skill 独立完成视频

默认智能体：GLM-5.3，开启思考。用其图片输入能力检查实际素材；若需要连续视频理解，先核验是否具有原生视频能力，或用关键时刻抽帧、接缝前后帧及连续播放补充。单张图、缩略图或文件名不能代替完整视频审查。

核心交付是视频：在 WorkBuddy 可用的 Flova 或已有影视创作平台中，使用我们的正式 Skill 冻结副本，规划或读取分镜、生成、审查、局部修复、剪辑及导出。平台调查和系统建议随这条真实生产轨迹交付。

## A. 先核验当前接入

检查客户端版本、实际工具、Skill 文件访问能力、创作平台、账号登录状态、图像与视频模型、可用额度、导出和素材下载方式。将外层对话模型、平台内部 Agent 与视频生成模型分开记录。

已接入平台可直接复用。优先使用平台提供的正式工具或 CLI。Flova 官方说明支持 WorkBuddy 等外部 Agent 接入，并提供自定义 Skill、项目推进和导出；这不意味着本机已经安装或账号权限已经具备。

需要 Flova CLI 时，读取当前官方安装说明：

https://cli.flova.ai/flovaCLI-setup.md

依照实际文档安装和核验，不能凭本执行书猜 CLI 命令或请求字段。登录步骤仅在真实需要时由用户完成；已有授权创作步骤继续推进。使用现有可用额度，不自行充值或购买新订阅。

## B. 载入真正的 Skill

从 CodeBuddy 交接中取得正式 Skill 主文件、依赖规则、绑定清单和输入状态。先核对哈希，逐份阅读。只有描述摘要、开工提示词或平台默认模板时，不得宣称已经测试了我们的 Skill。

保留源文件不变；在 WorkBuddy 工作区创建独立运行副本。允许做客户端路径、工具名与平台参数的必要映射，使用适配记录逐项写明源规则、目标工具、能力支持与行为差异。

首帧、参考图、尾帧和换机位重建的判断原则，应从真实 Skill 读取。不能为了让平台更容易出片，悄悄把我们的流程换成另一个社区模板。

若使用 Flova，由 WorkBuddy 将规则明确传递给实际负责生产的 Flova Agent，保存生效 Skill 文档或可见的加载证据，并查看项目中最终有效规则。外层 WorkBuddy 读过文件，不足以证明内部 Agent 已采用。

原始 Skill 与必要适配分开保留。如果平台规则或默认 Skill 冲突，记录并处理；不能关闭完成生产所必需的工具 Skill。无法实现的规则标为 unsupported 或 unknown，不隐瞒，不把受影响部分判通过。

主文件缺失时先继续接入核验和平台调查，标记主视频测试等待交接。可以另做平台能力试验，但不能将其充当本任务结果。

## C. 测试题目与规划条件

题目沿用写实“克苏鲁追船”：船上有船长和大副，包含威胁显现、应对、追赶升级及明确结果。角色身份、船、怪物、空间关系和关键动作因果持续一致。

已有批准剧本和分镜时使用冻结版本。不要重写剧情或减少困难镜头；技术上必须改变时逐项记录，结果降为部分可比。

没有现成分镜时，按我们的实际 Skill 自主完成故事和镜头规划，并在生成前冻结。记录每镜的叙事功能、起止状态、人物与道具、空间方向、生成方法、依赖、源素材时长及预期保留区间。此组命名为自主规划独立测试。

有现成成片规范时沿用；没有时，本版建议以 16:9、约一分钟以上的完整叙事作为工作目标，成片目标区间为 60–90 秒。不得靠重复静止镜头、片头或空白凑时长。不要为满足建议时长擅自改变已有批准分镜。

源镜素材至少 8 秒，默认 10 秒；成片保留时长单独决定。检查当前视频模型支持的实际时长，不能将两个不连续的短片拼接后冒充同一次合格源镜。平台无法满足下限时记录政策不满足，并明确本组不具完整等价性。

禁止旁白；保留合格环境声和原生音效。沿用本轮已批准的无主动配音政策，避免临时引入新的对白、配乐或配音系统；如冻结剧本本身含对白，先按其实际规则标记并单独验收，不擅自删掉关键剧情。

## D. 真实制作顺序

1. 核验或生产角色、船与怪物所需素材。参考图的风格要与写实目标一致；优先复用同一批合格输入。新建或编辑素材要记录原因和身份影响。
2. 确认分镜输入、参考绑定与依赖，按 Skill 选择合法生成方式。不预设每镜都必须直接尾帧接力，也不预设每镜都要重新建首帧。
3. 提交生成，保存实际 prompt、参考文件、关键参数、真实模型、任务标识和时间；平台不公开的内部参数写 unknown。
4. 检查完整源镜与拟保留区间，分别判断人物身份、环境连续性和重大不合理。特别看分身、换脸、额外人物、漂浮肢体、船体跳变、怪物尺度、追赶方向和关键接触。
5. 按现有 Skill 与修复上限做局部修复。保留首次结果、失败原因和每次修复，不能只交最终最佳片段。
6. 选定候选与保留区间。真实动作接力使用所选保留区间的最后一帧；上游裁切改变后，重新验证依赖。换机位依 Skill 重建构图，不能强迫沿用不适合的新首帧。
7. 装配并完整播放，检查接缝、声音和动作因果，最后导出可下载成片。

每一步以工具结果、项目状态和真实素材为证据。已知在途任务优先恢复，观察中断不代表生成失败。不要为了给进度答复而重复创建项目或重交任务。

## E. 记录什么，才能提出系统建议

记录规划、素材准备、模型或平台等待、查询、审查、返工、装配、人工等待和导出的时间。无法观察的平台内部阶段标为未观测。

区分完整墙钟时间与各镜累计生成时间。保存人工操作、手动改 prompt、选片、补交请求和导出帮助，避免把人主导结果写成自主成功。

每个建议用 WB-EFF 编号，写清真实问题、证据位置、平台如何处理、我们是否适用、迁移代价及最小验证方法。优先看任务推进、有效素材复用、局部恢复、轮询、托管、选版和裁切依赖，别只交泛泛架构建议。

跨平台成片更好，可能来自视频模型、内部规划、资源、修复、剪辑或执行方式。按证据拆分，不能直接宣布我们的系统完全没问题。

| 产物 | 内容 |
|---|---|
| PHASE52_WORKBUDDY_VIDEO_TEST_REPORT.md | 实际模型、Skill 加载、素材绑定、方法选择、失败、修复、介入、耗时与结论 |
| PHASE52_WORKBUDDY_SKILL_ADAPTATION.md | 源规则到平台执行的映射、差异及不支持项 |
| PHASE52_WORKBUDDY_TIMELINE.csv | 可核验事件与等待分类 |
| PHASE52_WORKBUDDY_EFFICIENCY_SUGGESTIONS.md | 有编号、证据和验证办法的系统建议 |
| 最终 MP4 | 可播放、可下载；项目链接作为补充 |
| 各源镜、首次失败和修复版本 | 文件名与 shot_id、attempt 对应，不能只有缩略图 |
| 裁切与端点记录 | 所选版本、保留区间、实际接力帧及依赖变化 |

首次完整候选完成后先保留并报告，不要求无限生成直到满意。依据已冻结修复上限结束；无上限配置时，先提出有限测试预算并完成可确认范围，达到预算就报告剩余失败。

如果平台禁止下载源素材、模型名称不公开、额度不足或导出受阻，逐项记录影响。没有完整成片时称未完成，不用调查报告代替视频交付。
